## Paraphrases

### Round 1 (reader)

**What this proposes.** Each OpenSpec change names its GitHub roadmap issue (`x-issue`) and the paths it may touch (`x-paths`) in `.openspec.yaml`. `tasks.md` gains a `## Discovered` section with `[blocks-PR]`, `[later]` and `[you]` markers. A `launchd` file watcher on the developer's Mac reads every worktree's changes through the pinned OpenSpec CLI and keeps one marked comment per issue up to date with the open backlog. It also sets Phase, Worktree and Open tasks on the private project. Before writing, it withholds items that match privacy patterns or a private denylist, and it rewrites mentions and issue references so nothing notifies anyone or creates a backlink. An `issues:gate` script blocks a PR while spec tasks or blocking items are open, or while the diff leaves `x-paths`. The review loop runs it first. A `/start-issue` skill creates linked worktrees.

**How the existing system works, per this plan.** Agents work in sandboxed worktrees with no `git push`, so the live backlog exists only in each worktree's uncommitted `tasks.md`. Inside the sandbox file watching does not work, so the watcher has to run outside it. OpenSpec 1.17 already parses changes: `instructions apply --json` gives the tasks, `status --json` gives which artifacts exist, and unknown `x-` keys in `.openspec.yaml` survive every command. The roadmap is a private user-owned GitHub project over issues in the public repo. Writing to the project needs a classic token with the `project` scope; issue comments need an Issues-write token.

Ruling: both paraphrases match the intent.

### Round 2 (reader)

**What this proposes.** Each OpenSpec change names its roadmap issue (`x-issue`) and its allowed paths (`x-paths`) in `.openspec.yaml`. Work found mid-apply goes under `## Discovered` in `tasks.md` with `[blocks-PR]`, `[later] #n` or `[you]` markers, or into a follow-up issue made by `issues:followup`. A `launchd` watcher outside the sandbox reads every worktree's changes through the pinned OpenSpec CLI. It keeps one marked comment per issue with the open backlog, and sets Phase, Worktree and Open tasks on the private project. Every published string first passes a pattern and denylist guard, and mentions and issue references are rewritten. An `issues:gate` blocks a PR on open blocking work or out-of-scope files. The review loop runs it in implementation mode, and `/start-issue` creates linked worktrees.

**How the existing system works, per this plan.** Agents work in sandboxed worktrees with no push, so the live backlog is only in each worktree's `tasks.md`, and file watching fails inside the sandbox. OpenSpec 1.17 returns each task's text, done flag and line but no groups, and it refuses archived changes, which live in `openspec/changes/archive/<date>-<name>/`. `x-` keys in `.openspec.yaml` survive every command. The roadmap is a private user-owned project over issues in the public repo: project fields need a classic `project` token, comments need an Issues-write token. Project skills live in `.agents/skills/` behind `.claude/skills/` symlinks, and the root `tsconfig.json` does not cover `scripts/`.

Ruling: both paraphrases match the intent.

### Round 5 (reader)

**What this proposes.** The sync already keeps one comment per roadmap issue, showing the open tasks of the OpenSpec changes that name it, and sets private project fields. Group 8 replaces the private Phase field with GitHub's preview issue status (Backlog, Todo, In progress, In review), derived from the change and rolled up to the least advanced. It is written with the issues token in its own request, only on open issues and only to statuses whose category is OPEN. Worktree and Open tasks stay as project fields, and the project's own Status is never written.

**How the existing system works, per this plan.** Agents work in sandboxed worktrees, and the live backlog is each worktree's `tasks.md`. A `launchd` watcher outside the sandbox reads it through the pinned OpenSpec CLI. Pure core modules decide, and thin edges call git, `gh` and the Keychain. A classic token writes the project and an issues token writes comments. The gate diffs against `origin/develop` plus `x-paths`. An archived change is detected from archive folders in any root or in `origin/develop`.

Ruling: both paraphrases match the intent.
