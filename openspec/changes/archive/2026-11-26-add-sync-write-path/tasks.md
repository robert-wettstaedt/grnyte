# Tasks

Worktree `1177-add-sync-write-path`, branch `feature/1177-add-sync-write-path`. Design decisions are cited as D1 to D16 (design.md). A twin is named by inserting `.powersync` before the last extension the import keeps (`write.powersync.ts` beside `write.ts`); PowerSync code and tests import twins by that explicit path.

The remote write functions the mutators replaced are deleted and merged (issue 1184, D15), and this branch starts from that merge. Each group below removes before it builds.

Database tests run on a throwaway Postgres, never the shared dev database: `ci/local.sh up` once and again after every edit to a migration it already applied (the migrator skips those), `ci/local.sh test <files>` per task, `ci/local.sh run <command>` for anything else that needs the CI environment, `ci/local.sh down` at the end. If `drizzle-kit generate` hangs in the sandbox, write the SQL file, the journal entry and the snapshot by hand and prove them with the migrator on the throwaway database.

## How the tests are written

The loop: one test, seen red, then only the code that makes it green, then the next test. The cases of a task are written in the order given, one cycle each; a table, a stream entry or a file arrives with the first test that needs it, never ahead of it. A test states one behavior in its name and reads its result through an interface a caller has, never by counting rows behind it, with one exception named below. Expected values are literals the test set up. Nothing of ours is faked except at the edges named per seam.

Seams (agreed with the user, 2026-11-25); no test is written at any other:

- W1, the write route. Interface: `handleSyncMutate(request)` and its `Response`. Real: Postgres, the mutators, the token check. Read back through the query definitions the screens use, run with the executor of `event/testContext.ts`. Faked: nothing; one test registry for deferred work, passed in as `handleMutate`'s tests pass theirs.
- W2, the client's `write()` in the PowerSync build. Interface: `write(mutation, opts)`, its result and its `WriteRejection`. Faked: `fetch`, the clock, the token source handed to `setWriteToken`, and `isOnline`, as `write.test.ts` fakes it.
- W3, the request pipeline for `/api/sync/`. Interface: a `Request` through the real hooks and the route, and its `Response`.
- R1, the server read. Interface: `readQuery({ as, name, args })` as a signed-in caller (`withLocals`). Real: Postgres with fixtures of its own (two regions, an event, a notification, a comment, a report), so no case passes on an empty table.
- R2, a resource over the server source. Interface: `createResource(...)` and its `data` and `phase`. Faked: `readQuery` (the network edge), `isOnline`.
- G1, the build guard. Interface: the plugin's `resolveId`, as `vite.sync-engine.test.ts` drives `zeroGuard`.
- T1, the change markers. Interface: SQL in, the marker row out. The exception to "never count rows": the row is what the trigger hands the stream.
- S1, what a device holds. Interface: the stream config through PowerSync's rules engine (`SyncedWorld` in `streams.server.test.ts`).
- C1, retention. Interface: `sweepAppliedWrites(before)`, seen through what the write route answers to a replay.
- Not tested on purpose: the CI step (seen green on the pull request), the five-line route file beyond W3, the generated schemas beyond the tests they already have, `engine.powersync.ts` (the token wiring and the account switch, both by the drive), docs, records and the privacy copy.
