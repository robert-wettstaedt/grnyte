# Proposal

## Why

grnyte's auth mails carry links, which open outside the installed PWA and the coming native app, and every sensitive action is confirmed by re-typing a password, which a person who signs in with Apple or Google will not have. GoTrue alone cannot fix either: its reauthenticate nonce is checked only for a password change, and a bare access token can change the password or a person's sign-in identities directly. This is change 1 of 3 built from the social-login grilling and released together with `add-social-sign-in` and `add-native-auth-handoff`: it lays the auth foundation the other two build on.

## What Changes

- **Codes instead of links.** Sign-up confirmation, password reset and email change mail an 8-digit code that works for 10 minutes. grnyte counts the tries at each code per address and refuses a 6th until a new code is sent. One shared code-entry screen part (length as a parameter, autofill on Apple devices, 60 s resend countdown, expired state) serves all of them and the 6-digit re-auth step. GoTrue's OTP length and lifetime are set explicitly.
- **Own re-authentication.** Deleting the account, deleting a region, handing over ownership, and changing or setting the password ask for a 6-digit code mailed by grnyte (not GoTrue): random, stored hashed, single use, void after 5 wrong tries, bound to the account, the session, the action and its target. A confirmed code writes a short-lived grant the action checks at its point of use. A re-auth screen that already has a live grant does not mail a code, and otherwise mails one only when the person presses "Send code" or submits the action unconfirmed. A confirmation never runs the action: every screen confirms first, then reveals its own fields and the person presses the action. An email change or a password change deletes the account's open codes and grants. The mechanism takes other confirmers, so `add-social-sign-in` can add "Confirm with Apple" without reshaping it.
- **Re-auth enforced inside GoTrue.** A database trigger on `auth.identities` refuses adding or removing a sign-in identity unless the account is being created in the same transaction, its email is unconfirmed, a fresh grant for that action exists (for adding, a grant bound to that exact identity), or (adding only) the identity is the authentication service's own email identity for the account's current address, or the provider owns the email's domain and the new identity's email equals the account's. Changing an identity's owner or provider is held to the same rule. The provider-owned domain list lives once, in SQL. GoTrue's "secure password change" is switched on.
- **Session revocation.** Auth, account and admin actions, the app API and every synced write refuse a session that no longer exists in `auth.sessions`; a synced write on such a session signs the device out instead of retrying, while a check that could not be made (a database error) fails as retryable and signs nobody out. The device that changes its password stays signed in, its other tabs included. Page loads and synced reads are not checked. Sessions have no age or idle limit: a sign-in lasts until it is revoked. Other devices are signed out automatically after a password change, reset or email change, and from a new settings button that asks for no re-authentication (GoTrue's own sign-out of other sessions needs only a token anyway). Settings also lists the signed-in devices (when each signed in and was last active; no device name, never the IP) and signs out one at a time, again without re-authentication.
- **Cross-site request refusal.** The server refuses a cookie-authenticated request with any method but GET or HEAD unless the browser marks it `Sec-Fetch-Site: same-origin`; Apple's `form_post` return and the Bearer-only app API are the only exceptions, and a request without the header falls back to Kit's Origin check. Kit already refuses cross-origin remote calls in production; the guard is defence in depth that also covers endpoints and form actions with non-form bodies, sibling-site requests and the dev server. The app API is exempt only because it never reads the cookie session.
- **Profile step.** Sign-up asks only for email and password. Every new account then passes a "complete your profile" step (username, grading scale preselected by the UI language, a terms notice) before any app screen opens; the original destination, such as an invitation, is kept. The admin sign-up alert moves to the end of that step. Accounts that never finish it are deleted after 7 days.
- **New sign-in and create-account screens.** `/auth/signin` and `/auth/signup` stay, lose the tab control, gain one switch line each, a password Show toggle and a marked first step where `add-social-sign-in` puts its choice of methods; both keep the terms line. Settings password loses its repeat field, and email change asks for its two codes one at a time. "Sign up" never appears beside "Sign in". The installed PWA opens on a welcome fork.
- **Contested sign-up under codes.** The `contested_signup` flag stays. An unconfirmed account is flagged before any second mail reaches it, except the Resend on the code screen right after sign-up (carrying a signed token from the sign-up response, and like sign-up asking for proof-of-work) and a sign-in with the right password; confirming a flagged account by code, from sign-up or from forgot password, replaces the stranger's password and leads to a required "choose your password" step, then the profile step.
- **Non-enumerating answers.** Sign-up with an address that already has an account mails that address an "already have an account" notice listing its sign-in methods; an email change to a taken address does the same. All of that work runs in the request, so a real failure (the authentication service down, the mail quota spent, the sign-up hook refusing) is shown instead of a false success. Timing is not equalised: telling an existing address from a free one through timing, sign-up then sign-in, the authentication service's own endpoints or a pending email change is an accepted, documented risk.
- **Per-person limits on code steps and sign-in.** Every server-side code call and password sign-in to the authentication service goes through the auth-only secret-key client from `migrate-supabase-keys`, which forwards the person's own address, so the service's per-IP limits count each person instead of grnyte's server as one bucket. One exception: the legacy `/auth/confirm` link verify stays on the cookie client until it retires, one link lifetime after the code-template push (its link carries no address to count). Every rate-limit refusal from the service alerts admins. A sign-up for a taken address mails its "already have an account" notice at most once a minute.
- **Password policy.** New passwords are checked against the Have I Been Pwned range API, with a bundled list of the 10,000 most common passwords as fallback, and capped at 72 bytes, on create, set, change and reset. A new password with leading or trailing whitespace is refused with an explanation, never trimmed, and is normalised to NFC before it is checked and stored; sign-in normalises to NFC as well.
- **Security mails and audit.** GoTrue's password-changed and email-changed notifications are switched on; grnyte mails its own notices for account deleted and ownership handed over. A new `auth_events` table records re-auth failures and mail-quota exhaustion, admins are alerted on spikes and on an exhausted mail quota, and GoTrue's own audit log is pruned at 90 days.
- **Open sign-up posture.** Public sign-up is switched on in GoTrue behind a before-user-created hook that refuses every email, phone and anonymous sign-up that did not come through grnyte's proof-of-work form, so `add-social-sign-in` can let provider sign-ups through. GoTrue moves to a release that has the hook and the notification switches (the branch's second local stack first, the shared local stack only after the release); `npm run check:prod` asserts the whole configuration.
- **GoTrue behaviour contract.** The GoTrue behaviours grnyte relies on but no release promises (what an admin password update mails and ends, the email change order, the send-wait answer, code length and lifetime, and more) are pinned by one test suite run against the second local stack, each test naming the grnyte code that depends on it. `check:prod`, which runs daily, fails when the hosted GoTrue version differs from the one the suite last passed on, and a runbook says how to move to the new one.
- **BREAKING (open tabs, one release):** the sign-up form drops its username and repeat-password fields, and the delete-account, delete-region, handover and change-password commands stop accepting a password. Their exports keep their names and only widen their arguments; a tab loaded before the deploy is refused with "reload this page" instead of a 404. `/auth/confirm` keeps working until the last link mailed before the code-template push has expired; `/auth/reset-password`, `sendPasswordReset` and the remote-form exports marked `@public` keep working for one release, so links mailed just before the deploy still land, then they are removed.

## Non-goals

- Apple and Google sign-in, the own OAuth client, `/auth/callback`, linking and unlinking UI, the sign-in methods section in settings, the "Signed up with Apple or Google?" hint, the last-used badge and "Confirm with Apple" on code screens: all `add-social-sign-in`. This change only defines the slots and contracts they plug into.
- Bearer-token app endpoints, the native browser handoff, `apple-app-site-association` / `assetlinks.json` and the Expo test app: `add-native-auth-handoff`.
- Passkeys and MFA. No "add a second sign-in method" prompt anywhere.
- German GoTrue mails. GoTrue's templates stay English with the code in the subject; a send-email hook is the recorded route if that changes.
- A Content Security Policy. It is a separate follow-up change after this feature, and it is needed: session tokens are readable by JavaScript (Zero needs them) and grnyte has no CSP, so any XSS is an account takeover.
- Moving GoTrue's codes (sign-up confirmation, reset, email change) onto grnyte's own mechanism. grnyte counts tries on its own path; guessing straight at GoTrue's `/verify` keeps only GoTrue's per-IP limit, a residual risk stated in design.md.
- A feature flag. Nothing deploys until all three changes and the outside setup are done.

## Capabilities

### New Capabilities

- `auth/email-codes`: 8-digit codes for sign-up confirmation, password reset and email change, the try count on grnyte's path, the shared code entry, contested sign-ups under the code flow, and email change to a taken address.
- `auth/reauthentication`: the code-based re-auth step, the grant an action checks at its point of use, and the database guard that holds GoTrue's own identity endpoints to the same rule.
- `auth/sessions`: session liveness on auth, account, admin and app-API requests and synced writes, no time limit on a sign-in, signing out other devices, and the signed-in devices list with per-device sign-out.
- `auth/cross-site-requests`: the refusal of cookie-authenticated cross-site requests that change something, and its two exceptions.
- `auth/profile-completion`: the profile step every new account passes, the gate in front of the app, and the admin sign-up alert.
- `auth/sign-in-screens`: the sign-in and create-account screens, the installed-app welcome fork, and the failed sign-in message.
- `auth/password-policy`: which passwords are accepted on create, set, change and reset.
- `auth/security-notices`: the mails that tell a person about their account (already exists, password and email changed, account deleted, ownership handed over).
- `auth/auth-events`: the auth event log, its retention, and the admin alerts on spikes and mail-quota exhaustion.

### Modified Capabilities

- `auth/sign-up-protection`: a reset for an unconfirmed address re-sends the confirmation code (flagging the account) instead of sending nothing; GoTrue's public sign-up is refused by a hook instead of being switched off; confirmation is by code, not link; the admin alert fires at profile completion, not at confirmation; accounts without a profile expire; the GoTrue behaviours grnyte relies on are pinned to a tested release, which the configuration check compares with the deployed one.
- `auth/account-deletion`: deletion is confirmed by re-authentication, not the current password; the screen names blocking regions before the code is asked for; a deletion mail goes to the address.
- `regions/region-deletion`: deletion takes a re-authentication and the region's name, not the password.
- `regions/region-ownership`: handover takes a re-authentication, not the password, and the previous owner is mailed.

## Resolved assumptions

Each was a choice no decision entry covered; the user ruled on all of them (2026-11-09). Specs, design and tasks follow these rulings.

1. **Resend right after sign-up does not flag.** The Resend on the post-sign-up code screen carries a signed token from the sign-up response and leaves the account unflagged; every other resend to an unconfirmed account flags it. (`auth/email-codes`)
2. **The right password on an unconfirmed account** re-sends the confirmation code and opens code entry, without flagging. (`auth/sign-in-screens`, `auth/email-codes`)
3. **A grant lasts 5 minutes and is single use**, as written. (`auth/reauthentication`)
4. **At most 5 re-auth mails per account per hour**, beside the 60 s countdown, as written. (`auth/reauthentication`)
5. **grnyte's password change writes through the admin API** after its own grant check and signs the device back in; grnyte sends the password-changed notice itself if GoTrue's admin path does not, as written. (`auth/reauthentication`, `auth/security-notices`)
6. **The password itself stays unguarded by the trigger**: a token on a session under 24 h can still change it through GoTrue; the password-changed mail and secure email change cover it, recorded in design.md Risks. (`auth/reauthentication`)
7. **A deleted account leaves a deletion marker** (`account_deleted` event; sign-in and the profile gate sign the caller out with an "account deleted" message; the next cleanup deletes it), as written. (`auth/account-deletion`, `auth/profile-completion`)
8. **GoTrue's audit log is pruned by `/api/tasks/cleanup`**, not pg_cron, as written. (`auth/auth-events`)
9. **`auth_events` keeps 90 days; a spike is more than 20 events of one failure kind in an hour**, alerted once per kind per day, as written. (`auth/auth-events`)
10. **grnyte's own code and notice mails are localised** by the account's contact language, as written. (`auth/security-notices`, `auth/reauthentication`)
11. **GoTrue's notification templates get a method-neutral "not me" line** pointing to the sign-in methods, as written. (`auth/security-notices`)
12. **Old tabs on the four re-auth commands get "reload this page"**, never the old password path; `sendPasswordReset` stays one release, as written. (`auth/reauthentication`)
13. **The welcome fork lives on `/auth/signin`** in the installed PWA, and the screens are described in design.md decision 13, with the design canvas from the auth screens review (2026-11-14). (`auth/sign-in-screens`)
14. **Grading scale preselection follows the UI language** (German: FB, English: V), not the country. (`auth/profile-completion`)
15. **Session liveness is checked on auth, account, admin and app-API endpoints plus every synced write**, not on every hooked request or page load. (`auth/sessions`)
16. **The handover mail goes to the previous owner**, as written. (`regions/region-ownership`)
17. **The region specs are rewritten to re-authentication** like the account specs, as written. (`regions/region-deletion`, `regions/region-ownership`)
18. **GoTrue's magic-link template carries no code**, only a notice, as written. (`auth/email-codes`)
19. **Re-auth codes are hashed with HMAC-SHA256 under a key derived from `SUPABASE_SECRET_KEY`** (label `reauth-code`, the derivation proof-of-work already uses); no separate secret (review round 2, P65). (`auth/reauthentication`)
20. **The trigger checks user, action and provider, not the session**; the session binding is enforced where the grant is written, recorded in design.md Risks. (`auth/reauthentication`)
21. **Sign-up's admin create carries `app_metadata.signup = 'grnyte'`**, as written. (`auth/sign-up-protection`)
22. **The re-auth mail names the action, not the target**, as written. (`auth/reauthentication`)
23. **The invite address mismatch copy is left to `add-social-sign-in`**, as written.
24. **A confirmation is spent inside the action's own transaction after its refusals**, as written. (`auth/reauthentication`)
25. **`ReauthStep` checks for a live grant before mailing a code** (moved here from `add-social-sign-in`), so a screen confirmed another way, or reloaded within 5 minutes, sends nothing; otherwise it mails a code only on "Send code" or when the action asks for one (review round 1). (`auth/reauthentication`)

26. **The sign-up resend token is valid 7 days (`UNCONFIRMED_MAX_AGE_MS`) and bound to the address only**: a holder can only re-send a code to the owner's inbox. (`auth/email-codes`)
27. **Passwords are normalised to NFC at sign-in too**: the web sign-in normalises on the server before calling GoTrue, and the native app before its direct GoTrue call, because hashing happens at sign-in too. A refused sign-in whose input NFC changed is retried once as entered, so a password stored decomposed before this rule still works. (`auth/password-policy`)
28. **GoTrue's codes are 8 digits, and grnyte counts tries on its own path** (review round 1, P1): 5 tries per address and code type, reset by a new code; re-auth codes stay 6 digits. (`auth/email-codes`)
29. **"Sign out other devices" asks for no re-authentication** (review round 1, P3): GoTrue's own sign-out of other sessions needs only a token, so a grant would guard nothing. (`auth/sessions`, `auth/reauthentication`)
