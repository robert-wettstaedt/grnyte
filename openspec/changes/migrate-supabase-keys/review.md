## Round 1

- Snapshot: frozen copy at `migrate-supabase-keys-r1` (the worktree guard refuses the temp-index commit recipe); code at develop `7e25d347`.

Reader paraphrases:

- What this proposes: "One code release moves grnyte off Supabase's legacy `anon`/`service_role` keys and its symmetric HS256 JWT secret, onto publishable/secret API keys (renamed variables) and asymmetric ES256 signing keys checked through a public JWKS URL. The verifier becomes a factory tested on both key types and gains an `unavailable` result; zero-cache stops verifying tokens so grnyte's get-queries and mutate endpoints are the only gate (with nginx per-address limits in front); PowerSync holds both key sources through the transition; and a new auth-only GoTrue client `supabaseAuthServer` sends the secret key plus `Sb-Forwarded-For`. A manual dashboard/Bitwarden/VPS runbook (steps 0 to 9) follows the release so every verifier accepts both token kinds from before Rotate keys until the legacy secret is revoked and removed."
- How the existing system works, per this plan: "`verify.server.ts` is the only place a token's `sub` becomes trusted: it reads the HS256 secret from `$env/static/private` and an optional JWKS URL, picks the key by `alg`, checks aud/role/contested, and maps every failure except expiry to `invalid`; the hook turns any failure into an anonymous request. The two Zero endpoints verify the forwarded Bearer token, zero-cache 1.11 additionally HMAC-checks every token itself with `ZERO_AUTH_SECRET`, and PowerSync does the same with `PS_SUPABASE_JWT_SECRET`. Browser and server clients use the anon key; `supabaseAdmin` and the proof-of-work HMAC use the service-role key. Secrets come from Bitwarden by uuid allowlists in the workflows; local development uses one shared self-hosted Supabase stack (GoTrue 2.167, HS256 only)."
