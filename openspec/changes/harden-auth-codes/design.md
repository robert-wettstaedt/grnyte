# Design

## Context

See proposal.md for why. This change builds on develop `7e25d347`, which includes commit `5bdb19f5` (the former password-reset fix), and on the change `migrate-supabase-keys`, released before it. The state it starts from:

- From `migrate-supabase-keys`: grnyte uses Supabase's new API keys (a publishable key in the browser, an `sb_secret_*` key on the server) and verifies JWTs with asymmetric signing keys. It provides, in `src/lib/auth/authServer.server.ts`, `supabaseAuthServer(event: Pick<RequestEvent, 'getClientAddress'>): AuthServer`, where `AuthServer` is a frozen allowlist of bound methods, shipped as `Pick<SupabaseClient['auth'], 'resend'>` only (its test asserts the keys are exactly `['resend']`); each later change adds the methods it calls, with its first caller and a test (no `admin`, `mfa` or data client ever): a fresh client per call with `SUPABASE_SECRET_KEY` as `apikey`, the shared `secretKeyFetch` (in `supabaseAdmin.server.ts`), which drops an `Authorization: Bearer` only when it carries an `sb_secret_` key and passes a person's own Bearer through, `sb-forwarded-for` from `event.getClientAddress()` (with `security_sb_forwarded_for_enabled` on, so GoTrue's per-IP limits see the person's own address), no stored session and no cookie written: a session a call returns is the caller's to write through `locals.supabase.auth.setSession`. It has no user-scoped variant; this change adds one, `supabaseAuthServerAs` (decision 9). Its ESLint `no-restricted-imports` rule keeps `SUPABASE_SECRET_KEY` out of every other module. It already moves the sign-up resend onto that client and derives the proof-of-work keys from `SUPABASE_SECRET_KEY`. It also removes zero-cache's own token check (`ZERO_AUTH_SECRET` goes), so grnyte's endpoints (`/api/zero/get-queries` and `handleMutate`) are the only place a synced request's token is checked, and when the JWKS cannot be fetched get-queries answers 502 (zero-cache retries) while mutate answers 401 (Zero goes to `needs-auth` and keeps queued writes; a 502 would end in Zero's error state and drop them). Its first apply task brings up this branch's second local Supabase stack (decision 4).
- Auth writes are SvelteKit remote functions: `signin.remote.ts`, `signup.remote.ts` (both under `src/routes/(landing)/auth/(tabs)/`), `forgot-password.remote.ts`, `reset-password.remote.ts`, `src/lib/auth/session.remote.ts` (`signOut`, `sendPasswordReset`), `src/routes/(app)/settings/account.remote.ts` (`updateEmailCommand`, `updatePasswordCommand`, `deleteAccountCommand`, `accountDeletionPreview`) and `src/lib/entities/region/regions.remote.ts` (`transferRegionOwnershipCommand`, `deleteRegionCommand`). AGENTS.md keeps auth and account on remote functions; nothing here becomes a mutator.
- Sign-up creates the GoTrue user with the admin API (`disable_signup` is true), inserts `users` + `user_settings` with the username in one `pinnedTx`, and mails a link through `mailSignupConfirmation` (`src/lib/auth/mail.server.ts`, which takes the Supabase client to send through). `/auth/confirm/+server.ts` verifies the link, handles `contested_signup` (`revokeContestedPassword`; on its `false` it sends the person to forgot password) and fires `notifyAdminsOfSignup`.
- `verifyAccessToken` (`src/lib/auth/verify.server.ts`) refuses a token whose `app_metadata` carries the contested flag. `authGuard` (`src/lib/hooks/auth.server.ts`) loads `getPageState` once per request in one `pinnedTx`, skips cookie claims entirely under `ZERO_API_PREFIX`, and bounces a signed-in caller off `/auth/*` by `event.url.pathname`; for a remote-function request Kit rewrites `event.url` to the CALLING page's path (`x-sveltekit-pathname`), so that bounce also hits remote calls made from auth pages. `requireAuthed` (`src/lib/remote/authed.server.ts`) and `handleMutate` (`src/lib/zero/mutate.server.ts`) both refuse a caller with no `users` row; `handleMutate` answers 401, which Zero turns into `needs-auth` and a refresh-and-resend every 30 s (`src/lib/zero/authRecovery.ts`). Nothing reads `auth.sessions`.
- `verifyPassword` (`src/lib/entities/user/password.server.ts`) is the only re-auth, called by `deleteAccount`, `deleteRegion`, `transferRegionOwnership` and `changePassword`; it builds a throwaway non-persisting Supabase client so it never touches the caller's cookies. `CurrentPasswordField.svelte` offers a "mail me a reset" link (`sendPasswordReset`).
- `(app)` is `ssr = false`; its `+layout.svelte` already has a client twin of the hook's region-less bounce, driven by `globalState.userRegionsResource`, and a `SIGNED_OUT` listener that wipes the device and replaces the document.
- Kit, in a production build only, refuses a non-GET remote-function request whose `Origin` differs from the page's, and a cross-origin POST/PUT/PATCH/DELETE with a form content type to any other route (`respond.js`). Under `npm run dev` it checks neither. After a response is generated, `event.cookies.set` throws.
- `sendEmail` (`src/lib/email/send.server.ts`) returns a boolean and folds Resend's `daily_quota_exceeded` and `rate_limit_exceeded` into a `retry` outcome, logged as `send failed (<name>) for <template>`. `logServerFailure` rows are alerted by `alertOnNewErrors`, grouped by message, about once a day.
- GoTrue mail templates are generated by `src/lib/email/templates.ts` + `generate.ts` into `emails/gotrue/` and pushed by `push-templates.ts`. The notification templates (password changed, email changed, identity linked/unlinked) already exist there. The shared local stack runs `supabase/gotrue:v2.167.0` from `<shared stack>/docker-compose.yml`, with a `pg-functions://` custom access token hook as precedent. That stack serves every session on this machine; this change never edits it (decision 4).
- `/api/tasks/cleanup` runs every retention sweep; `sweepUnconfirmedAccounts` deletes unconfirmed accounts after 7 days and profile-less sign-in records after 1 hour. CI has no GoTrue: it runs a bare `postgres:16` with `ci/shim.sql`, whose `auth.users` stub has only `id`, `email`, `created_at` and `email_confirmed_at`.
- The newest migration is `drizzle/0147_promotion_quarter_and_notification.sql`.

## Goals / Non-Goals

**Goals:**

- Fix the contracts `add-social-sign-in` and `add-native-auth-handoff` build on, so neither reshapes a screen or a table from this change.
- Every re-auth check sits at the point of use, inside the handler's own write, never in the screen.

**Non-Goals:** see proposal.md. Also: no Zero schema change (the new tables are outside `schema.ts`, so no client can query them; zero-cache's publication still covers schema `public`, so their rows replicate into its replica on the VPS like every public table: code hashes, auth events, and `auth_code_attempts`' lower-cased addresses, including ones with no account, which a privacy review should count as held there too), no mutator, no change to how `get-queries` authenticates reads (reads keep working for one access-token lifetime after a revocation, accepted below).

## Decisions

### 1. Code entry: one component, `CodeEntry.svelte`, beside `AuthField`

New `src/lib/auth/CodeEntry.svelte`, built on `AuthField.svelte` (label, `FormHint`, the Tab-safe `action` snippet) rather than a new input. `AuthField` today takes only `autocomplete` among input attributes, so it gains pass-through props `inputmode`, `pattern`, `maxlength`, `oninput`, `autocapitalize` and `spellcheck` (task 5.0; the profile step's username field passes `autocapitalize="none"` and `spellcheck="false"`):

```ts
interface Props {
  field: StoreField<string> // from the caller's createFormStore
  label: string // names the address or the action
  length: 6 | 8 // 8 for GoTrue's codes, 6 for grnyte's re-auth codes
  onsubmit: (code: string) => Promise<void> // runs once `length` digits are present
  onresend: () => Promise<void> // caller sends; component owns the countdown
  sentAt: number // ms epoch of the last send, drives 60 s countdown
  expiresAt: number // ms epoch, sentAt + 10 min; past it shows the expired state
  alternatives?: Snippet // change 2 renders "Confirm with Apple" here
}
```

The input is `autocomplete="one-time-code" inputmode="numeric" pattern="[0-9]*"` with `maxlength` from `length`, labelled, with errors as text (accessibility criteria for the code field). Its copy names the length ("We sent an 8-digit code", "Enter the 6-digit code"), one i18n key per length in both locales. Digits only are kept; at `length` it calls `onsubmit` once. The sign-up confirmation, reset and email-change screens pass 8 (GoTrue's codes, decision 5); `ReauthStep` passes 6 (grnyte's own codes, decision 2). The countdown and expired state are local `$state` with one interval; the expired notice and the resend row enter with `slide` at `motion()`. The countdown digits use `tabular-nums` and are not a live region; a polite live region announces only when resend becomes available. Pressing Resend flips it at once to "Code sent" and restarts the countdown from the press; if `onresend` fails, both roll back and the error shows.

In flight (`onsubmit` running) the input is read-only and "Continue" shows the pending spinner. A wrong code keeps focus in the field, selects its digits so the next typing replaces them, and announces the error through an `aria-live` line under the field; no shake. It is used by the create-account screen (sign-up confirmation), sign-in (unconfirmed account), forgot password, settings email (twice, one per address) and `ReauthStep`.

Transitions around it, all at `motion()` (`$lib/state/motion.svelte`): a screen that swaps form to code entry to new-password step (create account, sign-in, forgot password) cross-fades the swap with `fade`; the email page's first code step enters with `slide` under the address form, and the two code steps (current address, then new address) replace each other with `fade`; `ReauthStep`'s confirmed state replaces its code field with `fade`; its "Send code" button gives way to `CodeEntry` with `slide`, and the "needs a fresh confirmation" line `require()` adds enters with `slide`. Every swap runs one way (the outgoing state leaves, the incoming enters, never both moving against each other) inside one container that keeps its height through the swap, so the page below never jumps. The confirmed state's check icon enters with `scale`.

A "Continue" button below the field submits the same digits for a paste that does not fire `oninput`; on press it reads the input itself (a fill may fire no `oninput`), and with fewer than `length` digits it shows the length line and sends nothing, so a short code never spends a try; it is disabled while `onsubmit` runs, so the automatic submit and a press never send one code twice. `CodeEntry` renders no `<form>`, its input has no `name` (so `Form`'s `store.capture` never copies the digits into the screen's store and payload), and every control in it ("Continue", resend) is `type="button"`: on the re-auth screens it sits inside `Form`'s `<form>`, whose submit runs the screen's action.

Rejected: six one-digit boxes (iOS autofill fills only the focused field); a separate component per flow.

### 2. Re-authentication: challenge table, grant table, two remote commands

New `src/lib/auth/reauth.server.ts` (server API) and `src/lib/auth/reauth.remote.ts` (commands). Two tables, both RLS on with no policies, written on the privileged handle like `client_error_logs`:

- `reauth_challenges`: `id uuid pk`, `auth_user_fk uuid not null` (FK `auth.users` on delete cascade), `session_id uuid not null`, `action text not null`, `target text not null`, `code_hash text not null`, `attempts smallint not null default 0`, `expires_at timestamptz not null`, `created_at`. Unique on `(auth_user_fk, session_id, action, target)`: a new request replaces the row (upsert), which voids the previous code.
- `reauth_grants`: `id uuid pk`, `auth_user_fk uuid not null` (cascade), `session_id uuid not null`, `action text not null`, `target text not null`, `method text not null` (`'email_code'` here; change 2 widens the type with `'apple'`), `expires_at timestamptz not null`, `created_at`. Unique on `(auth_user_fk, session_id, action, target)`. A grant is spent by deleting it.

Internally the row is a "grant"; user copy says "confirmation" (CONTEXT.md, task 11.2). The server API every handler and later change uses:

```ts
export type ReauthAction =
  | 'account.delete' // target: auth user id
  | 'password.change' // target: auth user id (also "set first password")
  | 'region.delete' // target: String(regionFk)
  | 'region.transfer' // target: `${regionFk}:${userFk}`
// change 2 adds 'identity.link' and 'identity.unlink', which trigger rule 6 already reads
export interface ReauthCaller {
  authUserId: string
  sessionId: string
}

export async function reauthCaller(): Promise<ReauthCaller> // from locals.claims after requireLiveSession(); 401 without session_id
export async function voidReauth(authUserId: string): Promise<void> // deletes every open challenge and grant of the account
export async function voidReauthCodes(authUserId: string): Promise<void> // open challenges only, for changePassword's failure path
export async function issueReauthCode(
  caller,
  action,
  target,
  mail: { email: string; locale: string },
): Promise<{ sentAt: number; expiresAt: number }>
export async function verifyReauthCode(
  caller,
  action,
  target,
  code: string,
): Promise<'granted' | 'wrong' | 'expired' | 'void'>
export async function writeGrant(caller, action, target, method: 'email_code'): Promise<void> // change 2 adds 'apple' for its confirmer
export async function spendGrant(tx, caller, action, target): Promise<boolean> // DELETE ... RETURNING inside the handler's tx
export async function holdGrant(tx, caller, action, target): Promise<boolean> // SELECT ... FOR UPDATE, for a handler whose write is a GoTrue call
export async function hasGrant(caller, action, target): Promise<boolean> // peek, spends nothing
```

`add-social-sign-in` adds the `identity.*` actions, the `'apple'` method and `bindLinkGrant` with their first callers, so this change ships no export without a caller.

`hasGrant` is a read-only peek. `reauthGrantStatus` uses it for every action, so a screen knows whether it is already confirmed.

Remote functions, in `reauth.remote.ts`: commands `requestReauthCode({ action, target })` and `confirmReauthCode({ action, target, code })`, and query `reauthGrantStatus({ action, target })` over `hasGrant`. All use `reauthCaller()`, so a profile-less account can still re-auth (it cannot reach any action yet, but `password.change` must not depend on a profile). The client never holds a grant id: the handler finds the grant by its own key, so there is nothing to forge or replay. The status query tells a screen only "confirmed or not".

`voidReauth(authUserId)` runs after a password is written (`changePassword`, `setNewPassword`, so reset and the contested step too) and after the second email-change code (`confirmEmailChangeCode`): a code or grant issued before the account's credentials changed no longer counts.

Code: `crypto.randomInt(0, 1_000_000)` zero-padded. Hash: HMAC-SHA256 over `challengeId:code` under a key derived from `SUPABASE_SECRET_KEY` with the label `reauth-code` (no secret of its own; see "Derived keys" below), compared with `timingSafeEqual`. A plain hash of 6 digits falls to a million guesses offline (proposal, resolved assumption 19). Wrong entry increments `attempts` in the same statement that reads the row (`UPDATE ... RETURNING`); the fifth wrong entry deletes the row. Lifetimes: code 10 min (the ASVS ceiling for out-of-band codes, and short enough to hold in memory while switching apps), grant 5 min. The mail goes through `sendEmail` in the request (decision 9), localised by `user_settings.contact_locale` with the request locale as fallback, subject `"<code> is your grnyte code"`, body naming the action. At most 5 issues per account per hour. The count cannot come from `auth_events`, whose writes are best-effort and never fail the request; nor from `reauth_challenges` itself, whose rows are replaced per action and target, so they never add up to an hour's issues. It is counted in the windowed counter of decision 5 (`auth_code_attempts`, `subject` = the auth user id, `kind = 'reauth_issue'`, a one-hour window), in the same transaction that upserts the challenge, before anything is mailed: a failed count fails the issue and nothing is sent.

Derived keys. No new secret exists. After `migrate-supabase-keys`, `src/lib/forms/proofOfWork.server.ts` derives labelled keys as `createHmac('sha256', SUPABASE_SECRET_KEY).update(label)`; on top of that, this change moves that one line into new `src/lib/auth/keys.server.ts` as `labelledKey(label: string): string` (the hex digest, which is what the altcha secrets take; callers that need bytes decode it). `proofOfWork.server.ts` imports it with its existing labels unchanged (so open challenges stay valid across the deploy), and the ESLint `no-restricted-imports` allowlist for `SUPABASE_SECRET_KEY` swaps `proofOfWork.server.ts` for `keys.server.ts`, which is now the module that reads it; and every keyed use in the three changes takes a label of its own: `reauth-code` (code hashes), `signup-resend` (resend tokens, decision 5), and in `add-social-sign-in` and `add-native-auth-handoff` the sealing helper's key. A label is never reused for two purposes. Rotating `SUPABASE_SECRET_KEY` therefore invalidates every open re-auth code, resend token, sealed OAuth cookie and handoff row at once; each lives minutes (resend tokens: 7 days, after which the next resend just flags), so the cost is a failed step and a retry (Risks).

Point of use. Each handler checks the grant inside the transaction that does the work, after its own refusals, so a refusal rolls the spend back:

- `deleteAccount` (`src/lib/entities/user/delete.server.ts`): inside its `pinnedTx`, after `classifyRegions` returns no blockers, `spendGrant(tx, caller, 'account.delete', authUserFk)`; false throws a `reauthRequired` result. The same tx also runs `delete from auth.sessions where user_id = $1`, so every session ends in the same step, and inserts the `account_deleted` auth event (the deletion marker, decision 7) directly on `tx`, not through the never-throwing `recordAuthEvent`, so the marker exists exactly when the deletion committed.
- `deleteRegion` (`src/lib/entities/region/delete.server.ts`) and `transferRegionOwnership` (`ownership.server.ts`): replace `verifyPassword` with `spendGrant` inside their existing locked transaction, after the name and recipient checks.
- `changePassword` (`account.remote.ts`): the work is a GoTrue call, not a DB write, so it opens its own tx, `holdGrant` locks the grant row, the GoTrue call runs, then `spendGrant` deletes the row and the tx commits. supabase-js answers a refusal as `{ error }` and does not throw, so the handler throws explicitly on `error`, which rolls the tx back and leaves the grant for a retry; a second concurrent call waits on the lock and then finds no grant. The GoTrue call inside the tx carries a timeout (5 s, an `AbortSignal` on the admin client's fetch), because it holds a pooled connection across HTTP; one line beside `pinnedTx`'s own note says so. On a refusal or a timeout the password may still have changed at GoTrue, so that path voids the account's open codes (`voidReauthCodes`) but keeps the grant for the retry (user decision, 2026-11-15): a transient failure then costs only another Save, and the grant still expires in 5 minutes and is bound to this session and action. Only a successful change runs the full `voidReauth`. The automatic sign-outs after a password change, reset or email change call GoTrue directly and need no grant.

`verifyPassword` and `password.server.ts` are deleted once these four callers move. Each result union swaps `{ kind: 'wrongPassword' }` for `{ kind: 'reauthRequired' }`, which the commands map to `refuseCommand(formError('auth_reauthRequired'), 'code')`.

New `src/lib/auth/ReauthStep.svelte` wraps `CodeEntry`: props `action`, `target`, a bindable `confirmed: boolean`, `ready: boolean` (default true; see below), optional `alternatives` snippet passed through, and an exported `require()` the screen calls. A confirmation never runs the action (auth screens review, 2026-11-14): every screen confirms first and the person then presses the action, so an irreversible deletion or handover never starts from the 6th digit, and there is one mode to build and test. Every caller renders it inside a `{#key}` block keyed on action and target, so moving between two regions or two recipients on one route (`regions/[regionId]/owner/[userId]`) starts the step over. On mount it reads `reauthGrantStatus` and nothing else, and reserves the height of its unconfirmed card (the "Send code" card) while that loads (a skeleton after about 250 ms, per AGENTS.md), so neither the confirmed state nor "Send code" pushes the screen when it lands:

- On mount the step sets `confirmed` to false before it peeks, so a page component Kit reuses between `/regions/1/delete` and `/regions/2/delete` never shows region 2 confirmed while its peek is pending. A live grant (a confirmation from another confirmer, or a reload within 5 minutes) then shows the confirmed state and sets `confirmed`. Like `CodeEntry`, the step's own controls ("Send code") are `type="button"`, since it renders inside `Form`.
- Otherwise it shows a "Send code" button and mails nothing. Pressing it calls `requestReauthCode` and swaps to `CodeEntry`; a correct code calls `confirmReauthCode`, shows the confirmed state and sets `confirmed`. Nothing else runs.
- The screen reads `bind:confirmed`: it reveals its own fields (the new password, the region's name) with `slide` at `motion()`, and enables its submit, which is the header's `PageHeaderAction` through `Form`; that button shows the pending spinner while the command runs. Screens without fields (account deletion, handover) only enable the submit.
- When the screen's command answers `reauthRequired` (no grant, or it expired or was voided before the submit), the screen calls `require()`: `confirmed` goes back to false, the fields hide with their values kept in the form store, a code is requested at once, and `CodeEntry` shows with a line saying the action needs a fresh confirmation. After the code the fields show again filled, and the action runs on the next submit.

It replaces `CurrentPasswordField` on `settings/account/delete`, `settings/password`, `regions/[regionId]/delete` and `regions/[regionId]/owner/[userId]`; the region-blocking list on the delete screen renders below it, as today (it comes from a query and must never push the step), and a blocked deletion offers no "Send code" at all. A prop `ready` (default true) keeps the step in its reserved skeleton until the screen has what decides it: account deletion and region delete pass their preview query (`accountDeletionPreview`, `regionDeletionPreview`) having settled, answered or failed, so "Send code" never shows and then vanishes, and a fast live-grant peek never reveals region delete's name field before the preview card above it. A prop `blocked` (account deletion's blocking regions) settles the step into a one-line state of the same height ("Hand over the regions below first") with no "Send code" and no alternatives. On region delete the order is intro, `ReauthStep`, the existing preview card, then the revealed name field, so neither a late preview nor the reveal inserts above rendered content.

Rejected: GoTrue's `reauthenticate` nonce (only `PUT /user` with a password checks it); one table with a `verified_at` column (an Apple confirmer would have to fake a challenge row); passing a grant token through the client; mailing the code on mount (a screen opened to read the blocking list, or opened twice, burns codes and the hourly cap).

### 3. `auth.identities` trigger and marker triggers

One custom SQL migration (`drizzle-kit generate --custom`) adds, all `SECURITY DEFINER` with `search_path = ''`, owned by `postgres`. The SQL is idempotent (`create or replace function`, `drop trigger if exists` before each `create trigger`), and every environment, the hosted prod project included, gets it through `npm run migrate`, never by hand, so drizzle's journal and the database always agree. The hosted projects are migrated only at release, from the merged branch: drizzle applies only migrations newer than the last one a database recorded, so migrating a hosted database from this branch early would make it silently skip any other branch's migration that was generated earlier but merged later. There is no hosted dev project; everything else is rehearsed on the second local stack. Before release, task 3.5 proves on prod, inside a transaction that is always rolled back (with `set local lock_timeout = '2s'`), that the triggers, `deleteAccount`'s `auth.sessions` delete and `isSessionLive`'s read of it are allowed.

- `public.mark_auth_user_created()`: `AFTER INSERT ON auth.users`, runs `set_config('grnyte.auth_user_created', NEW.id::text, true)`.
- `public.mark_auth_user_deleting()`: `BEFORE DELETE ON auth.users`, runs `set_config('grnyte.auth_user_deleting', OLD.id::text, true)`. Both markers hold a comma-separated list of ids, since one statement can create or delete several accounts and their cascades run after its last row (task 3.3).
- `public.guard_auth_identity()`: `BEFORE INSERT OR DELETE OR UPDATE OF user_id, provider, provider_id ON auth.identities FOR EACH ROW`. An UPDATE is checked as an insertion of `NEW` (rules 1, 3, 4, 5 and 6 with `identity.link`); the other columns GoTrue updates on every sign-in (`identity_data`, `last_sign_in_at`, `updated_at`) do not fire it. Let `uid` be `NEW.user_id` or `OLD.user_id`, `provider` be `NEW.provider` or `OLD.provider`. Allowed when any holds, checked in this order:
  1. `current_setting('grnyte.auth_user_created', true) = uid::text` (account created in this transaction);
  2. on DELETE, `current_setting('grnyte.auth_user_deleting', true) = uid::text` (cascade of an account delete);
  3. `auth.users.email_confirmed_at IS NULL` for `uid` (GoTrue linking a provider onto an unconfirmed account strips the stranger's password and removes the email identity; that stays allowed);
  4. on INSERT only, `NEW.provider = 'email'` and `lower(NEW.identity_data->>'email') = lower(u.email)`: GoTrue's own email identity for the account's current address. GoTrue adds one when a social-only account sets its first password (`ensureEmailIdentityForPassword`) and at the final verify of a secure email change (`createNewIdentity`). This adds no sign-in path that the password itself does not already open, so the accepted risk "the password is not guarded by the trigger" is unchanged by it; Applied, task 3.7: GoTrue `v2.197.0` adds no email identity when a social-only account sets its first password, and at the final verify of a secure email change it writes the new address's email identity BEFORE it updates `auth.users.email`, so rule 4 also accepts the account's pending `auth.users.email_change` address (only GoTrue's two-code verify reaches that write);
  5. on INSERT only, the provider owns the account's email domain and the new identity's email equals the account's: `lower(split_part(u.email, '@', 2)) = ANY (public.provider_owned_domains(NEW.provider))` and `lower(NEW.identity_data->>'email') = lower(u.email)` (the auto-link `add-social-sign-in` allows for provider-owned addresses);
  6. `DELETE FROM public.reauth_grants WHERE auth_user_fk = uid AND expires_at > now() AND` either (INSERT) `action = 'identity.link' AND target = NEW.provider || ':' || NEW.provider_id` or (DELETE) `action = 'identity.unlink' AND target = OLD.provider`, `RETURNING` finds a row; the delete spends it. A link grant counts only once change 2's `bindLinkGrant` has named the exact identity, so it cannot be spent on any other one.
     Otherwise `RAISE EXCEPTION ... USING ERRCODE = '42501'`.
- `public.provider_owned_domains(provider text) returns text[]`, `IMMUTABLE`: `google` gives `gmail.com`, `googlemail.com`; `apple` gives `icloud.com`, `me.com`, `mac.com`, `privaterelay.appleid.com`; anything else an empty array. This is the one definition of the list; `add-social-sign-in` reads it through this function and keeps no TypeScript copy.

Rule 5 is what lets `add-social-sign-in`'s provider-owned auto-link through without a grant: no session exists before the sign-in, so a grant there would have to be faked. It also refuses an identity whose email differs from the account's, so a provider cannot attach itself to an account at an owned domain by reporting another address. Rule 4 is restricted to `provider = 'email'` and the account's own address, so it cannot be used to attach a social identity.

The trigger cannot see the GoTrue request's session, so the session half of the binding is enforced where the grant is written (`writeGrant` takes the session from verified claims) and the trigger checks user, action and provider. A transaction-local marker is used rather than comparing `xmin`, because GoTrue may update `auth.users` in the same transaction before linking an identity to an existing account, which would make an `xmin` test pass for a link.

Contract for change 2: rule 6 reads the action names as text, so this change's SQL tests insert `identity.*` grants directly; change 2 adds `identity.link` and `identity.unlink` to `ReauthAction` and adds `bindLinkGrant(caller, provider, sub)`, which re-targets the caller's own `(identity.link, provider)` grant to `${provider}:${sub}`. Link calls `hasGrant(caller, 'identity.link', provider)` to answer nicely, then runs its own link flow. Its callback verifies the provider's token, checks the token's subject is the one its own flow started for, calls `bindLinkGrant(caller, provider, sub)` and only then asks GoTrue to link; the trigger spends the bound grant. So the spend happens only on that flow: a GoTrue link call made directly with a stolen session and another identity finds no grant naming that identity (see Risks). Unlink peeks `hasGrant(caller, 'identity.unlink', provider)` and the trigger spends it. Change 2 never writes or spends an `identity.*` grant itself, and writes no grant for a provider-owned domain sign-in (rule 5 covers it).

If the hosted project refuses triggers on `auth.identities` or `auth.users`, the fallback is detection only: the identity-linked and identity-unlinked notification mails tell the owner, and nothing refuses the change.

### 5. Codes in GoTrue mails

Forgot password mails a confirmation code to an unconfirmed address (after flagging it) and a recovery code to a confirmed one, so one verify serves both. On success it reads `isContested` exactly as `confirmSignupCode` does and runs the same contested handling (`false` answers `forgotPassword` again), then `{ next: 'choosePassword' }`.
- `setNewPassword({ password })`, used by the reset and by the contested step, refuses unless the session's `amr` claim holds an `otp` entry whose timestamp is under 10 minutes old, which only a code just verified on this session produces. GoTrue issues every `POST /verify` session with the `otp` method (`models.OTP` in its `verify.go`), the recovery and contested paths included, and never writes `recovery`, so `otp` is the one value checked; task 7.4 asserts the `amr` each of the three real verifies produces (measured on v2.197.0: `otp` for all three). One `NewPasswordStep.svelte` (password field with Show toggle) renders both. `setNewPassword` sits in the session ratchet's documented carve-out (decision 8): it checks `amr` instead of a grant.
- `confirmEmailChangeCode({ email, code })` in `account.remote.ts` (type `email_change`), called once per address; after the second, `voidReauth`, `refreshSession()` and `signOut({ scope: 'others' })`. The settings email page asks for one code at a time (auth screens review): first the current address's ("confirm it's you"), then the new address's, each step a `CodeEntry`, swapped with `fade`. GoTrue mails both codes in the one `updateUser({ email })` call, so the new address's code is already on its way during the first step and its 10 minutes run from then; the second step says so. Any resend of an email change (`updateUser` again or `resend({ type: 'email_change' })`) runs GoTrue's `sendEmailChange`, which mints new codes for BOTH addresses and resets `email_change_confirm_status` to zero, so an accepted first code stops counting. Therefore the resend on either step re-sends both codes and returns the page to the first step with a line saying both addresses got a new code. The step the page shows comes from `confirmEmailChangeCode`'s answer, never from a count: it answers `done` only when GoTrue's verify returned a session whose `user.email` is the new address, and `next` (show the other address's step) when GoTrue accepted a single confirmation (no session); only `done` runs `voidReauth`, `refreshSession()` and the sign-out of other sessions.
- `resendSignupCode({ email, resendToken?, pow, honeypot })`: like `signUp`, it requires a fresh proof-of-work solution and an empty honeypot, refusing before anything else. With a valid `resendToken` for this address it only re-sends; without one it flags first (`flagContestedSignup`), then `mailSignupConfirmation` (resolved assumption 1). Same answer whatever the address, unless the send fails (decision 9).

The resend token is `<exp>.<mac>`, `mac` = HMAC-SHA256 under the derived key labelled `signup-resend` (decision 2) over `signup-resend|<lower-cased email>|<exp>`, compared with `timingSafeEqual`, `exp` = issue time plus `UNCONFIRMED_MAX_AGE_MS`, 7 days, bound to the address only (resolved assumption 26: a holder can only re-send a code to the owner's inbox). `signUp` returns one for every address, existing or not, so its presence reveals nothing; the page keeps it in the form store, so a reload drops it and the next resend flags. Helpers `issueResendToken(email)` / `checkResendToken(email, token)` live in `src/lib/auth/contested.server.ts` beside `flagContestedSignup`.

Guess counting on grnyte's path. GoTrue counts no failed tries per code, so grnyte counts its own per address. The per-IP side is GoTrue's own limit, which sees the person's address through `supabaseAuthServer` (decision 9). New table `auth_code_attempts`: `subject text not null` (the lower-cased address; the auth user id for `reauth_issue`), `kind text not null` (`'signup' | 'recovery' | 'email_change'`, the GoTrue code type being guessed; `'reauth_issue'`, decision 2's hourly mail cap; `'already_has_account'`, decision 9's one notice per minute, subject the address), `tries smallint not null default 0`, `window_started_at timestamptz not null default now()`, primary key `(subject, kind)`, RLS on with no policies, written on the privileged handle. It is not `reauth_challenges`: those rows are keyed by account, session, action and target, carry the code's hash and reference `auth.users`, while a GoTrue code is checked before any session exists, for an address that may have no account, and grnyte never sees its hash, so every column but the counter would be faked. Helpers in new `src/lib/auth/codeAttempts.server.ts`:

```ts
export type CodeKind = 'signup' | 'recovery' | 'email_change'
export async function takeCodeTry(email: string, kinds: CodeKind[]): Promise<boolean> // false when any kind is past 5 tries
export async function clearCodeTries(email: string, kind: CodeKind): Promise<void>
```

Windows. Every count is a fixed window that starts at the first try: one statement, `INSERT ... ON CONFLICT DO UPDATE SET tries = CASE WHEN window_started_at < now() - <window> THEN 1 ELSE tries + 1 END, window_started_at = CASE WHEN window_started_at < now() - <window> THEN now() ELSE window_started_at END RETURNING tries`. A refused try still counts but never moves the window, so hammering a locked key does not extend its lock. The windows are 10 minutes for the address kinds (a code's lifetime, so a count never outlives the code it was guessing), 1 hour for `reauth_issue` and 60 seconds for `already_has_account`.

`takeCodeTry` counts the try before GoTrue is asked, so concurrent tries cannot slip past the limit; any kind over 5 answers false, and the step refuses with `auth_codeLocked` ("Too many tries. Request a new code.") without calling GoTrue. A correct code clears the row. `confirmSignupCode` counts `signup`. `confirmResetCode` counts `recovery`, and `signup` as well only when the address's account is unconfirmed (read from `auth.users` first), because only then does its `type: 'email'` verify also guess a confirmation code; so wrong sign-up confirmations for a confirmed address cannot lock its owner's reset. `confirmEmailChangeCode` counts `email_change` for the address it is given. Every grnyte send of a new code of a kind clears that kind for that address: `signUp` and `resendSignupCode` and sign-in's unconfirmed resend (`signup`), forgot password (`recovery`; for an unconfirmed address both `signup` and `recovery`), the email change request (`email_change` for both addresses). The clear runs in the request right after the send, and only once GoTrue answered that send with success: a refused send (`over_email_send_rate_limit`, or any `error`) leaves the same live code in place, so it leaves the count too. Otherwise 5 tries and a refused resend would repeat forever. A code requested straight from GoTrue clears nothing, which only makes the count stricter. The app-API twins in `add-native-auth-handoff` call the same bodies and inherit it. `sweepAuthLogs` also deletes rows whose window started more than a day ago.

Sign-in (`signin.remote.ts`): on `email_not_confirmed` (GoTrue checks the password first) it re-sends without flagging and returns `{ confirm: email, resendToken }`, and the page swaps to `CodeEntry` (resolved assumption 2). Every other error maps to `auth_invalidCredentials`, so a failed sign-in never says whether the address has an account. On success it checks the deletion marker (decision 7) before answering. An old sign-in tab renders only form-level `invalid()` issues, never a field of a successful result, so for one release the new page sends a hidden marker field `codeFlow=1`, and a submission without it gets today's `invalid(auth_emailNotConfirmed)` instead of `{ confirm, resendToken }` (decision 14). The code is still re-sent either way.

`mail.server.ts` keeps `mailSignupConfirmation`; `mailPasswordReset` drops `redirectTo`. Both already take the client to send through; callers pass `supabaseAuthServer(event)` (decision 9).

### 8. Sessions

New `src/lib/auth/session.server.ts`:

```ts
export async function isSessionLive(db, claims: { sub: string; session_id: string }): Promise<boolean>
// select 1 from auth.sessions where id = $session_id and user_id = $sub; live when found.
// A failed read (pooler error, timeout) throws; it never answers false.
export async function requireLiveSession(): Promise<void>
// cookie path: locals.claims; not live -> signOut({ scope: 'local' }) to clear cookies, throws 401
// a thrown read becomes a 503 and changes nothing
// locals.backendUnavailable (a JWKS or GoTrue outage left locals anonymous) -> 503 auth_serviceUnavailable, nothing else
```

Only verified claims whose `auth.sessions` row is absent lead to `auth_sessionEnded`. When the hook could not verify the token because the backend was unreachable (a JWKS outage sets `backendUnavailable` with anonymous locals), "no claims" is not a dead session: `requireLiveSession` answers 503 `auth_serviceUnavailable`, signs nothing out and deletes nothing, so the client never wipes the device for an outage.

Only an absent row ends a session; nobody is signed out because the database blinked. For a remote command a failed read answers 503 and the person retries. For a synced write the read is not a new failure point: `handleMutate` already loads the caller with `loadSessionUser` in one `pinnedTx` (`mutate.server.ts`), and the `auth.sessions` read runs inside that same transaction, so a failed read fails exactly as a failed user load does today, with today's push behaviour (zero-cache retries a failing push a few times, then the client rejects the queued writes).

Sessions have no age or idle limit: a session lives until it is revoked, as in consumer apps generally, so no device is ever signed out (and wiped, unsynced writes included) for time alone. Theft is answered by revocation (password and email changes, signing out other devices), the security notices, and fresh re-authentication for every sensitive action.

The check runs on writes and account actions, and nowhere else (resolved assumption 15): page loads and `read()` in the hook stay as they are, and synced reads continue until the access token expires.

- Auth and account: `reauthCaller()` calls `requireLiveSession()` first, so every re-auth command and every handler that spends a grant is covered; the rest of `settings/account.remote.ts` (email change and its codes), `session.remote.ts` (`signOutOthers`) and `completeProfile` call it directly. Sign-in, sign-up, forgot password and their code confirms run before a session exists and are not checked; `setNewPassword` runs on the session a code just made and checks `amr` instead (decision 5). Client half: `requireLiveSession` refuses with the stable form error `auth_sessionEnded` (status 401). Every path a refusal reaches the screen by (`createFormStore().submit` for forms, `notifyError`/`withUndo` for one-press commands such as "Sign out other devices", `remoteResource`'s error phase for remote queries such as `accountDeletionPreview` and the admin lists), and `ReauthStep`'s own calls and grant peek, recognise that key and call `wipeAndLeave(resolve('/'))` from `$lib/state/wipe` directly, instead of showing it as error text: `requireLiveSession` already cleared the cookies, and calling the wipe itself needs no browser Supabase client, so it also works on `(landing)` pages such as `/auth/profile`, which have none.
- Admin: every remote function that calls `requireAppAdmin` calls `requireLiveSession()` beside it.
- Every synced write: `handleMutate`'s loader calls `isSessionLive` and answers 401 for a dead session, as for an unverifiable or expired token. After `migrate-supabase-keys` zero-cache checks no token itself, so `handleMutate` and `/api/zero/get-queries` are the only gate, and their 401s are what put Zero into `needs-auth` (when the JWKS cannot be fetched, get-queries answers 502, which zero-cache retries, and mutate answers 401 like an expired token: Zero goes to `needs-auth`, the refresh at GoTrue succeeds, and the write is retried until the JWKS answers again; nothing signs out, because only a definitive refresh refusal does). A distinct answer would not reach the client: zero-cache maps both 401 and 403 push answers to `needs-auth` and replaces the body. What tells the cases apart is the refresh that `needs-auth` triggers: an expired token refreshes, a dead session cannot (its row is gone, so GoTrue refuses its refresh token). So the `needs-auth` watcher in `(app)/+layout.svelte` (with `startAuthRecovery` in `src/lib/zero/authRecovery.ts`) treats a refresh that GoTrue refused DEFINITIVELY as signed out instead of re-arming every 30 s. Definitive means the refresh token or its session is gone: GoTrue's `refresh_token_not_found`, `session_not_found`, `refresh_token_already_used`, or a 400 invalid-grant answer. Anything else (offline, a GoTrue 5xx, a 429, a timeout) is not proof of anything, and auth-js keeps the session on those, so the watcher re-arms exactly as today. On a definitive refusal it first re-reads the cookie session once (`getSession()`), and only if that holds no newer session than the one Zero used does it call `supabase.auth.signOut({ scope: 'local' })`, whose existing `SIGNED_OUT` listener wipes the device and leaves for `/` (`wipeAndLeave(resolve('/'))`). The re-read is what keeps a tab of the same browser signed in after another tab changed the password (decision 6).
- App API: change 3's Bearer path calls `isSessionLive` on every request under its prefix.

A ratchet in `src/lib/remote/gates.test.ts` lists the auth, account and admin remote exports and fails when one is added without reaching the check. Its documented carve-out: the pre-session exports (sign-in, sign-up, forgot password, their code confirms and resends) and `setNewPassword`, each with its reason.

`session.remote.ts` gains `signOutOthers` (command: `requireLiveSession`, then `signOut({ scope: 'others' })`); settings shows it as a row that acts at once and ends with a success toast. It asks for no re-authentication: GoTrue's `POST /logout?scope=others` accepts a bare access token anyway, so a grant on grnyte's button would guard nothing (see Risks).

Signed-in devices (auth screens review, 2026-11-14). `session.remote.ts` also gains the query `signedInDevices` and the command `signOutDevice({ id })`, both after `requireLiveSession`. ### 9. Mail and address-dependent work in the request, and GoTrue's per-IP limit

Everything runs inside the request; there is no after-response work and no hosting-specific API (no `waitUntil`, nothing Vercel-only), so the app keeps running on any Node host. Sign-up, resend, forgot password and email change do their GoTrue calls and mails before they answer, and a real failure is shown instead of a false success:

- GoTrue unreachable or answering 5xx: `auth_serviceUnavailable` ("Something went wrong on our side. Try again in a minute.").
- Mail quota or send limit (Resend's quota error, GoTrue's `over_email_send_rate_limit`): `auth_mailUnavailable` ("We could not send the mail right now. Try again later."), also logged through `noteMailRefusal` (decision 12).
- The before-user-created hook refusing a sign-up: `auth_signupRefused`.

Everything else keeps the non-enumerating wording: a sign-up for a taken address answers "check your inbox" like any other and mails `alreadyHasAccount`, at most once per address per 60 seconds (counted in `auth_code_attempts`, `kind = 'already_has_account'`, a 60-second window; a skipped send still answers success), so the notice cannot be used to bomb an inbox; an email change to a taken address answers like any change and mails the taken address; forgot password answers "check your inbox" for an unknown address. Timing is not equalised, and the remaining ways to tell an existing address from a free one are an accepted risk (Risks).

GoTrue's per-IP limit and grnyte's server-side calls. Every code call grnyte makes to GoTrue (`verifyOtp` for sign-up, reset and email change; `resend`; `resetPasswordForEmail`; `signInWithPassword` for sign-in, its raw retry and the re-sign-in after a password change; `updateUser({ email })`; sign-in's unconfirmed resend; and their app-API twins in `add-native-auth-handoff`; the one exception is the legacy `/auth/confirm`, decision 14) goes through `supabaseAuthServer(event)` from `migrate-supabase-keys`, which sends the person's address (`event.getClientAddress()`) as `Sb-Forwarded-For` with the secret key. With `security_sb_forwarded_for_enabled` on, GoTrue's own per-IP limits (about 30 verifies per 5 minutes) then apply per person instead of to grnyte's server as one shared bucket, so grnyte keeps no per-IP limiter of its own. The email change, which acts as the signed-in person, calls `supabaseAuthServerAs(event, locals.verifiedToken)` with the caller's branded `VerifiedToken`; the secret key never travels as `Authorization: Bearer`.

The user-scoped variant. `migrate-supabase-keys` ships no user-scoped call, so this change adds a sibling in the same file, `src/lib/auth/authServer.server.ts`:

```ts
export type AuthServerAs = Pick<AuthClient, 'linkIdentity' | 'updateUser'>
export function supabaseAuthServerAs(event: Pick<RequestEvent, 'getClientAddress'>, user: VerifiedToken): AuthServerAs
```

`VerifiedToken` is a branded `{ accessToken: string; claims: VerifiedClaims }` that only `verifyAccessToken` returns (the hook keeps it on `locals` beside `claims`), so a caller cannot pair `locals.claims` with a token from elsewhere: the type cannot be built by hand, and the function also refuses a pair whose token's `sub` and `session_id` differ from the claims.

A sibling rather than an option, so the common unscoped helper keeps its shape and a call site's name says whether it acts as a person. It is built like `supabaseAuthServer` (secret key as `apikey`, `secretKeyFetch`, which leaves the seeded user Bearer alone because it strips only an `sb_secret_` one, `sb-forwarded-for`, `autoRefreshToken: false`, a frozen allowlist of its own two methods) but with `persistSession: true` and an explicit `storageKey` over a fresh in-memory `storage` per call, seeded under that key with `{ access_token: user.accessToken, refresh_token: '', expires_at: <now + 1 year>, token_type: 'bearer', user: { id: claims.sub } }`. `persistSession: true` is required: with it false, auth-js ignores the given storage and keeps its own empty memory store, so the seed is never read. auth-js reads the stored session before `updateUser` and `linkIdentity` (so a per-request Bearer through the fetch alone would fail with "session missing"), and it refreshes any stored session within 90 s of `expires_at`; with `refresh_token: ''` that refresh (`_callRefreshToken('')`) throws before any request is sent, and the call errors. So `expires_at` is set far in the future on purpose: it only stops auth-js's client-side refresh. It does not extend the token's validity: `verifyAccessToken` checked `claims.exp` before the caller had `claims` at all (the type admits only verified claims), and GoTrue checks the JWT's own `exp` again on the call. Its allowlist holds only the two methods that need a person; everything else stays on `supabaseAuthServer`. `admin` stays absent from both. `shortcut:` seeding storage is supabase-js's only stateless way to act as a user; if a release breaks it, the two calls move to GoTrue's REST endpoints (`PUT /user`, the link endpoint) with the Bearer per request.

`supabaseAuthServer`'s allowlist ships with `resend` only. This change adds the three methods it calls through it, each with its first caller and a test: `verifyOtp` (the sign-up, reset and email-change confirms), `resetPasswordForEmail` (forgot password) and `signInWithPassword` (sign-in and the re-sign-in after a password change; the caller writes the session with `locals.supabase.auth.setSession`) (tasks 7.12e, 7.12f). ### 11. Password policy

New `src/lib/auth/passwordPolicy.server.ts`: `checkPassword(password): Promise<'ok' | 'breached'>`, SHA-1 prefix range query to `api.pwnedpasswords.com/range/` with `Add-Padding: true` and a 1.5 s timeout, falling back to a bundled `src/lib/auth/common-passwords.txt` (top 10,000, server-only import). Called by `signUp`, `setNewPassword` and `changePassword` before any write; refusal is `formError('auth_passwordBreached')` on the password field.

Shape lives in `passwordSchema` (`src/lib/forms/schemas.ts`), which only new-password forms use (sign-up, change, reset; sign-in has its own field). `zod/mini` has no `.transform` method, so the schema is a pipe:

```ts
export const passwordSchema = z.pipe(
  z.string(...).check(z.refine(noSurroundingSpace, { error: formError('auth_passwordSpaces') })),
  z.transform(normalizePassword),
).check(z.minLength(8, ...), z.refine(within72Bytes, { error: formError('auth_passwordTooLong') }))
```

1. Leading or trailing whitespace (`/^\s|\s$/`) is refused with `formError('auth_passwordSpaces')`, which says why; nothing is trimmed.
2. `normalizePassword` normalises to NFC (`String.prototype.normalize`, inside the browser floor), so the breach check, the length rule and GoTrue all see the normalised value.
3. Min 8 characters, max 72 bytes via `TextEncoder`, measured after normalising.

The exact `zod/mini` spelling is the implementer's; what matters is that the length checks run on the normalised output.

Sign-in normalises too, so a password stored NFC matches whatever form a keyboard types: `signIn` in `signin.remote.ts` calls `normalizePassword` on the server before `supabaseAuthServer(event).signInWithPassword` (decision 9) and writes the returned session through `locals.supabase.auth.setSession`; the Expo app normalises before its direct GoTrue call. The "unconfirmed branch" is `signIn`'s handling of an `email_not_confirmed` answer to that same call (decision 5's sign-in paragraph); `add-native-auth-handoff` lifts it into a body of its own for `signin/unconfirmed`, which runs the same normalise-and-retry on the password it receives. A password stored before this rule in a decomposed form would no longer match, so when GoTrue answers `invalid_credentials` and the raw input differs from its NFC form, sign-in retries once with the raw input (the user rated a lockout here a medium inconvenience, not a rare one to accept). Whichever attempt GoTrue answered last is the one every later check reads: success with the contested and deletion-marker checks, `email_not_confirmed` with the code flow. The retry costs one more slot of GoTrue's per-IP limit, which is the person's own because sign-in is forwarded, and only for non-NFC input; the stored hash is not rewritten, since that would mail a "password changed" notice. Sign-in never refuses or trims whitespace, so a password set before this rule with a surrounding space still works. `normalizePassword` in `src/lib/forms/schemas.ts` is the only place the form is chosen.

### 16. Cross-site requests

New `src/lib/hooks/crossSite.server.ts` exports `crossSiteGuard: Handle`, first in `src/hooks.server.ts`'s `sequence`, so a refused request costs nothing else. A request is refused with a plain-text 403 (a hook error renders through `src/error.html`, so no i18n key) when all hold:

1. its method is not `GET` or `HEAD`;
2. it carries a Supabase auth cookie (`sb-*-auth-token`, chunks included), so it is cookie-authenticated;
3. it has a `Sec-Fetch-Site` header whose value is not `same-origin` (`same-site`, `cross-site` and `none` are all refused; grnyte is single-origin);
4. it is not exempt.

Without the header (an old browser, a non-browser client) the guard passes it on and Kit's own Origin check applies.

It is defence in depth for future cookie-authenticated `+server.ts` endpoints and for dev, not the only line, and in a production build it protects no route that exists today. Kit already refuses a non-GET remote-function request whose `Origin` is not the page's, and a cross-origin form-content-type POST/PUT/PATCH/DELETE to any other route; a form action given a non-form body answers 415, and the app has no form actions. What the guard adds, exactly:

- a future cookie-authenticated `+server.ts` endpoint that accepts a non-form content type (`application/json`, `text/plain` read as text) from another site, which Kit's form check skips, including `Sec-Fetch-Site: same-site` (a sibling subdomain) and `none`;
- `npm run dev` and `vite dev`, where Kit checks nothing at all, so a dev session on a real browser is not open to every page the developer visits.

Exempt, by one exported list `CROSS_SITE_EXEMPT` in the same module, matched on `event.request.url`'s pathname (never `event.url`, which Kit rewrites to the calling page for a remote request, so a remote call made from an exempt page would otherwise inherit the exemption):

- `POST /auth/callback/apple`: Apple's `form_post` arrives cross-site by design; `add-social-sign-in` answers it with a 303 to a same-origin GET and reads no session on it.
- every path under `APP_API_PREFIX = '/api/app/'`, a new export of `src/lib/hooks/auth.server.ts` beside `ZERO_API_PREFIX`. The exemption is safe only because no handler there can see the cookie session: `authGuard` treats `APP_API_PREFIX` exactly like `ZERO_API_PREFIX`, setting anonymous locals and never reading cookie claims, so `locals.claims` is always empty there and the app API reads only its Bearer header. One constant drives both the exemption and the cookie blindness, and `add-native-auth-handoff` reuses it.

The fallback is detection only: the identity-linked and identity-unlinked notifications tell the owner, and nothing refuses the change. Task 3.5 finds out early without migrating: there is no hosted dev project, so it creates the triggers and deletes from `auth.sessions` on prod inside a transaction it always rolls back, with `set local lock_timeout = '2s'` so it gives up rather than queue sign-ins behind its locks.
- [Migrating a hosted database from a branch] → drizzle applies only migrations newer than the last one a database recorded, so a database migrated from this branch would silently skip any other branch's migration generated earlier but merged later. Hosted environments are migrated only at release from the merged branch, and `0148`/`0149` are regenerated last, just before merging.
- [GoTrue deletes identities before the user row on account delete] → The deleting marker would not be set and deletion would fail. The trigger test runs `admin.deleteUser` and the unconfirmed sweep against the second local stack's GoTrue; a failure moves the marker to a `BEFORE DELETE` statement-level trigger or adds an `account.delete` grant exemption.
- [A GoTrue release reorders sign-up writes or stops nulling the stranger's password] → Server tests against the second local stack's GoTrue pin sign-up, the link onto an unconfirmed account (simulated by inserting an identity row while unconfirmed) and the contested scenario.
- [GoTrue writes the new email identity before updating `auth.users.email` on a secure email change] → Rule 4 would refuse it for a social-only account. Task 3.7 drives that change through the second local stack's GoTrue and pins the order.
- [Admin password update sends no notification] → Resolved assumption 5: grnyte sends its own (task 8.7).
- [Hosted GoTrue upgrades without notice and changes a behaviour grnyte relies on] → The behaviour contract (decision 17): `check:prod` fails on the new version, the suite on the second stack names the code to fix. Blind between the rollout and the next `check:prod` run, at most a day (the daily `post-deploy.yml` workflow runs it).
- [Rotating the secret key] → Every derived key changes with it (decision 2), so open re-auth codes, resend tokens, sealed OAuth cookies and handoff rows stop verifying at once. Each lives minutes (a resend token up to 7 days, after which the next resend flags as for any other), so the cost is one failed step and a retry. Accepted in exchange for having no second secret to provision and rotate.
- [Resend Free quota drained by one attacker] → Accepted; the error alert says so the same day.
- [HIBP slow] → 1.5 s cap then the bundled list.
- [Session check adds a read] → Only on auth, account, admin and app-API requests and synced writes (resolved assumption 15); page loads pay nothing. Accepted: a revoked session keeps loading pages and reading synced data until its access token expires, and its next write or account action signs it out at once.
- [Direct guessing of GoTrue's codes] → On grnyte's path the per-address counter (decision 5) stops guessing after 5 tries per code. What remains is GoTrue's own `/verify` called directly, limited to 30 per 5 minutes per IP with no per-code count, while a reset can be re-requested every 60 s so guesses run back to back across fresh codes. At 8 digits each code is a 1 in 100,000,000 target. At 100 IPs, about 864,000 guesses a day, that is about 0.9% a day against one targeted account, but it adds up: about 23% over a month and about 96% over a year of steady guessing. At 1000 IPs, about 8.6 million guesses a day, it is about 8.3% a day. The targets are a confirmed account's reset code, GoTrue's own `/otp` sign-in code (which the hook does not stop for an existing account), and the confirmation code of an address someone pre-registered. The owner does see it: a code mail arrives about every 10 minutes for as long as it runs. Accepted; watch supabase/auth#2819 (per-token failed-attempt limit) and adopt it when it ships.
- [A secret key bypasses RLS] → `supabaseAuthServer` carries the `sb_secret_*` key, which would bypass row-level security if it were ever used for a data query. It cannot be: `migrate-supabase-keys` returns only `client.auth` (no `.from`, `.rpc`, `.storage`, `.functions` or `.schema`, by type and by test) and its ESLint `no-restricted-imports` rule keeps `SUPABASE_SECRET_KEY` out of every module but `supabaseAdmin.server.ts`, `authServer.server.ts` and (after this change) `keys.server.ts`. This change adds no rule of its own; a lint rule on `.from(` would add nothing once only `.auth` is returned. Fails if someone extends that allowlist to build their own secret-key client.
- [The forwarded address is only as good as `getClientAddress()`] → GoTrue limits per the address grnyte forwards. On the current host that is the real client; under `adapter-node` behind a proxy without `ADDRESS_HEADER`, every person would share the proxy's address again (decision 9, recorded in `deployment/README.md`). GoTrue 429s are logged and alerted either way, and raising GoTrue's verify rate limit on the hosted project is the lever.
- [Enumeration of addresses] → Sign-up, forgot password and email change keep the non-enumerating wording, but other signals still tell an existing address from a free one, and this is accepted: the work runs in the request, so the answers take measurably different times (creating an account hashes a password, a taken address does not); signing up with an address and a password and then signing in with the same pair answers "confirm your email" for an address that was free and "invalid credentials" for one that already had an account (through grnyte or GoTrue's `/token` directly); an email change followed by `GET /auth/v1/user` shows `new_email` only when the address was free; GoTrue's own `/otp`, `/resend` and `/recover` already answer differently; a real failure (mail quota on the `alreadyHasAccount` mail) shows only for an existing address; and a second sign-up or forgot password for the same address within 60 seconds is refused by GoTrue's per-address send cooldown for a new or unconfirmed address (which gets a GoTrue mail) but answered as success for a confirmed one (whose `alreadyHasAccount` limit answers success). Proof-of-work on sign-up and resend and GoTrue's per-IP limits (which see the real address through `supabaseAuthServer`) make it slow to do at scale.
- [The counter lets an attacker spoil a person's code] → Five wrong tries through grnyte lock that address's current code of that kind for grnyte's screens; the person presses Resend, which resets the count. Wrong sign-up confirmations cannot lock a confirmed account's reset, because the reset step counts the sign-up kind only for an unconfirmed address (decision 5). An attacker can repeat it, costing the owner a resend each time; accepted, since it cannot take the account.
- [Android has no email-code autofill] → Only Apple devices offer a mailed code above the keyboard. On Android the person copies the code (Gmail's "Copy code") or types it; 8 digits is longer to type than 6. Accepted for the guessing margin.
- [The password is not guarded by the trigger (resolved assumption 6)] → A bare access token on a session younger than 24 h can still change the password through GoTrue directly, and on a social-only account that also adds the `email` identity rule 4 allows. The password-changed mail and secure email change are the cover. Fails if the owner ignores the mail.
- [Task 3.9's stop path puts a call back on the shared bucket] → If prod shows a forwarded call is not limited per person, that call returns to `locals.supabase`, where GoTrue counts every person against grnyte's one server address: about 30 wrong tries from anywhere then refuse that step for everyone for 5 minutes. A redeploy inside the release window; accepted only as the fallback, and admins are alerted by the 429 log.
- [A stolen session lives until revoked] → Sessions have no time limit (decision 8). A stolen session keeps working until the owner changes the password or email or signs out other devices; the password-changed and email-changed notices tell them, and every sensitive action needs a fresh code, so it cannot take the account, with one exception: within 24 hours of its sign-in a session can still change the password at GoTrue directly (see the unguarded-password risk), which the password-changed notice reports. Accepted, as in consumer apps generally; a forced expiry would wipe unsynced writes on every device.
- [Signing out other devices is not guarded] → `POST /logout?scope=others` (or `global`) needs only an access token, so a stolen session can sign the owner's other devices out, through GoTrue or grnyte's own button, which asks for no re-authentication either. With `scope=global` it signs out every device, and each of the owner's devices then wipes itself at its next write (decision 8), losing any offline work that had not synced yet. Accepted: it cannot take the account, the owner signs in again, and the cost is the unsynced work.
- [The trigger cannot see the session (resolved assumption 20)] → The attack this opens: with a stolen session an attacker calls GoTrue's link endpoint with the attacker's own provider identity over and over, until the victim, on their own session, confirms an `identity.link` for that provider; a provider-only grant would then be spent by the attacker's call and attach the attacker's identity, a persistent backdoor. Closed by binding: an `identity.link` grant counts in the trigger only after change 2's callback has rebound it to the exact provider subject its own flow verified (change 2's `bindLinkGrant`), so the attacker's identity never matches. Fails if change 2 binds a subject it did not verify on that flow.
- [The provider-owned domain list drifts] → Defined once in `public.provider_owned_domains`; `add-social-sign-in` reads the function and keeps no copy.
- [A password set before NFC normalisation in a decomposed form] → It was stored as typed, and sign-in now normalises, so it no longer matches. Closed by the one raw-input retry on `invalid_credentials` when NFC changed the input. Fails if such a person types the composed form instead: neither attempt matches, and forgot password recovers.
- [A legitimate flow sends `Sec-Fetch-Site: same-site`] → Refused by design; grnyte is single-origin. The 375 and 1280 drives of every form in task 15.3 would show it.

## Migration Plan

0. `migrate-supabase-keys` is released first, to prod, through its runbook step 5 (new keys live, `security_sb_forwarded_for_enabled` on, its forwarding probes passed, and no "Vercel appends" stop recorded); the three auth changes stay off develop until then. The second local stack (`<second stack>/`, compose project `supabase-keys`) stays up until the last auth change has merged.
1. Local, in the worktree: on the branch's second local Supabase stack (brought up by `migrate-supabase-keys`), apply this change's GoTrue settings (task 1.1), migrate its database, run the server tests.
2. Before merge, prod is only probed, never migrated (task 3.5, always rolled back). There is no hosted dev project: the release order below is rehearsed in full on the second local stack first.
3. Prod, after merging and after `0148`/`0149` were regenerated last on the branch: `npm run migrate` (tables, hook function, trigger; inert until the hook is enabled), deploy the app together with changes 2 and 3 (nothing ships before all three are done), then in one window push the code templates, enable the hook, set OTP length 8 and expiry 600, secure password change, the notification switches; run task 3.9's per-person probe for the code steps and for password sign-in (a failure there stops the window: the failing call goes back to `locals.supabase`, or rollback per step 5); then `disable_signup=false` last, after the hook is confirmed active; `check:prod`. One link lifetime after the template push, retire `/auth/confirm` to a redirect to `/auth/error` (decision 14), since no new mail carries a link any more and the last one mailed has expired. Between the deploy and the template push, new mails still carry links, which the kept `/auth/confirm` and `/auth/reset-password` still handle; after it, a tab loaded before the deploy shows its old screens until it reloads (decision 14).
4. Shared local stack: after the release, from the main checkout only, bump `<shared stack>/docker-compose.yml` to the pinned tag and env and migrate the shared dev DB, as its own announced step.
5. Rollback: set `disable_signup=true` and disable the hook, re-push the link templates (`emails/` is gitignored, so: check out the previous release's `src/lib/email/templates.ts`, run `npm run generate` with the public origin, then `push-templates.ts`), then revert the deploy. The new tables and triggers are inert without callers except the identity guard, which only refuses identity changes nothing in this release makes.
