# Plan review: harden-auth-codes

Status: stale

Closed after the round-4 confirmation by the user's decision; round-4 findings applied without a further round.

## Round 1

- Snapshot: frozen copy at `harden-auth-codes-r1` (the worktree guard refuses the temp-index commit recipe); code at HEAD `c1a37fa8` (= develop), plus branch `fix/password-reset-unstuck` (f9899c44), which the plan named as a prerequisite. Since then develop moved to `7e25d347`, which contains that branch as commit `5bdb19f5`.

Reader paraphrases:

- What this proposes: "Auth mails stop carrying links: sign-up confirmation, password reset and email change mail a 6-digit, 10-minute GoTrue code typed into one shared `CodeEntry`. Sensitive actions (delete account, delete region, hand over ownership, change or set password, sign out other devices) stop asking for the password; grnyte instead mails its own HMAC-hashed code whose confirmation writes a 5-minute grant bound to (user, session, action, target), spent inside the handler's own transaction, and a trigger on `auth.identities` holds GoTrue's own identity endpoints to the same rule. Around that: a profile step and gate (sign-up asks only email and password), a session-liveness check with a 90-day cap on account/admin/auth writes and synced writes, a `Sec-Fetch-Site` cross-site guard, a password policy (HIBP, NFC, 72 bytes, no surrounding whitespace), security notices, an `auth_events` log with admin alerts, and open GoTrue sign-up gated by a before-user-created hook."
- How the existing system works, per this plan: "Auth and account writes are SvelteKit remote functions. Sign-up creates the GoTrue user through the admin API (public sign-up off), inserts `users` + `user_settings` in one `pinnedTx`, and mails a link; `/auth/confirm` verifies the link, handles the `contested_signup` flag by replacing the stranger's password, and alerts admins. `verifyPassword` is the only re-authentication, used by four handlers. `verifyAccessToken` refuses contested tokens, `authGuard` loads page state once per request, `requireAuthed`/`handleMutate` refuse a caller with no `users` row, and nothing reads `auth.sessions`. GoTrue templates are generated in-repo and pushed by hand; the cleanup task sweeps unconfirmed accounts after 7 days and profile-less records after 1 hour."

## Round 2

- Snapshot: frozen copy at `harden-auth-codes-r2`; code at develop `7e25d347`. Range: diff `harden-auth-codes-r1/` against `harden-auth-codes-r2/`.

Reader paraphrases:

- What this proposes: "Auth mails stop carrying links: sign-up confirmation, password reset and email change mail an 8-digit, 10-minute GoTrue code typed into one shared `CodeEntry`, and grnyte counts tries per address and code kind, refusing a 6th. Deleting the account, deleting a region, handing over ownership and changing or setting the password stop asking for the password; grnyte instead mails its own 6-digit HMAC-hashed code whose confirmation writes a 5-minute grant bound to (user, session, action, target), spent inside the handler's own transaction, and a trigger on `auth.identities` holds GoTrue's own link and unlink to the same rule. Around that: a profile step and gate (sign-up asks only email and password), session liveness with a 90-day cap on writes, account and admin actions (plus a cleanup sweep), a `Sec-Fetch-Site` cross-site guard, a password policy (HIBP, NFC, 72 bytes, no surrounding whitespace), security notices, an `auth_events` log with alerts, and open GoTrue sign-up behind a before-user-created hook. All work whose cost depends on the address runs after the response."
- How the existing system works, per this plan: "Auth and account writes are remote functions. Sign-up creates the GoTrue user through the admin API (public sign-up off), inserts `users` + `user_settings` in one `pinnedTx`, and mails a link; `/auth/confirm` verifies it, handles a contested account through `revokeContestedPassword`, and alerts admins. `verifyPassword` (a throwaway non-persisting client) is the only re-authentication, used by four handlers. `verifyAccessToken` refuses contested tokens; `authGuard` loads page state once, skips cookies under `ZERO_API_PREFIX`, and bounces signed-in callers off `/auth/*` by `event.url`, which Kit rewrites to the calling page for remote calls. `requireAuthed`/`handleMutate` refuse a caller with no `users` row, and `handleMutate`'s 401 puts Zero into a 30 s refresh loop. Nothing reads `auth.sessions`; Kit checks Origin only in production builds; `sendEmail` folds quota errors into `retry`; the cleanup sweeps unconfirmed accounts after 7 days and profile-less records after 1 hour; CI has no GoTrue."
