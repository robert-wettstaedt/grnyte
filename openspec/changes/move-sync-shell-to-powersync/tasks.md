## How the tests are written

The loop: one test, seen red, then only the code that makes it green, then the next. The cases of a task are written in the order given, one cycle each; a file or an export arrives with the first case that needs it. A test names one behavior and reads its result through an interface a caller has. Expected values are literals. No refactoring inside the loop. A case marked (guard) holds already: it is seen red by the edit named with it, then reverted.

Seams (agreed with the user, 2026-11-25); no test is written at any other:

- S1, the connection and the store. Interface: `initPowerSync`, then `isOnline()`, `syncConnection()` and `storeBlocked()`. Faked: the PowerSync SDK (as `db.svelte.test.ts` does), `navigator.locks`, `fetch` (the probe), the clock, the browser's events. Real: `online.svelte.ts`, the lock rule.
- Z1, the Zero client in a PowerSync build. Interface: `initZero`, then `isOnline()`. Faked: the client, `fetch`, the clock.
- A1, the stored session. Interface: `checkSession` and its answer, and what the auth client then has stored. Faked: the auth client (an in-memory session and a refresh that answers as told).
- W1, the client's `write()`. Interface: its result or rejection, and the requests it sends. Faked: `fetch`, the clock, the auth client. Real: `checkSession`.
- R1, a resource over the server source. Interface: `createResource(...)`'s `data` and `phase`, and whether the tab leaves. Faked: `readQuery`, the auth client, the exit.
- E1, the engine's start. Interface: `start()`'s answer (a session, nothing, or a promise that stays open), `sessionMoved`, a `write()` or a server read after it, and whether the tab leaves (widened with the user's agreement after review round 5). Faked: the SDK, `zero-svelte`, `$env/dynamic/public`, the auth client, `fetch`, `readQuery`, the exit.
- G1, the importer list. Interface: `vite.sync-engine.test.ts`, as it stands.

"The exit" is `wipeAndLeave` and `location.reload`, which jsdom cannot follow. A refresh is counted at the auth client, since a second one is a request to the service; nothing of ours is counted. Not tested on purpose: `lock.ts` on its own, the layouts, `StatusBar`'s markup, `recoverSignIn` (moved; `authRecovery.test.ts` covers what it calls), the ping handler. Those are driven.
