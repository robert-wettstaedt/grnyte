# Proposal

## Why

The coming Expo app cannot call SvelteKit remote functions, cannot carry grnyte's cookies, and cannot receive an OAuth redirect on an `https` URL, so every auth step that `harden-auth-codes` and `add-social-sign-in` put on grnyte's server is out of its reach today. This is the third of three social-login changes, released together with the other two: it finishes auth once, for web and native, so the native project builds screens and no new auth features.

## What Changes

- **App API.** Small JSON endpoints under `/api/app/v1/` for every server-owned auth step, including the code steps that gained server rules (contested sign-up, password policy, signing other devices out): proof-of-work sign-up, sign-up code confirm and resend, a fresh code for an unconfirmed account after a password sign-in, forgot password and reset confirm, new password, the profile step, email change (taken-address notice included) and its codes, password change, re-auth code request and confirm, account deletion (Apple revocation included), sign-in methods with link and unlink, and sign out other devices. Each endpoint runs the same handler body as its web remote function, so one rule governs both, behind request and response shapes of its own that only widen, apart from three fixed answers every app must handle (a security refusal, "update required", "v1 retired").
- **Bearer only there.** The server hook reads `Authorization: Bearer <jwt>` on `/api/app/` and nowhere else, verifies it with the existing `jose` check, and refuses it when its session no longer exists; an outage of the signing keys or the session store answers 503, never a sign-out. On that prefix cookies are never read and never set, no CORS headers are sent, and only `application/json` bodies are accepted. Because it reads no cookie, the prefix is the Bearer exception to `harden-auth-codes`'s refusal of cross-site cookie requests. Calls that act as the person go through `harden-auth-codes`'s `supabaseAuthServerAs`, the one user-scoped client.
- **Native browser handoff as an app carrier.** The app starts Google sign-in (both platforms) and Apple sign-in on Android at `POST /api/app/v1/oauth/start`, registering an S256 PKCE challenge; the endpoint creates the app transaction in a server table keyed by the hash of its `state` and returns the provider's authorize URL. The provider returns to the same `/auth/callback/<provider>` the web uses, and `add-social-sign-in`'s callback finds the flow through its carrier list: this change's app carrier claims it by `hash(state)`, so issuer, nonce, signature and linking checks run once for both. The app carrier sets no cookie and lands on the app's return with a one-time code that lives 60 seconds, is stored hashed, and is spent by one atomic update: on iOS an https return that iOS hands only to grnyte's app (`/app-return`, caught by the auth session through `preferUniversalLinks`, iOS 17.4 or later), on Android the private-use scheme `rocks.grnyte:/auth`. Client impersonation through the scheme channel stays possible and is an accepted risk (design.md, Risks). The app names its return channel at the start, checked against an allowlist. The app trades the code, with its PKCE verifier (required on both platforms), for a session. App-started flows set no web cookies. The same handoff links Google or Apple from the app's sign-in methods screen. No second return URL is registered with Apple or Google.
- **Native Apple on iOS.** `expo-apple-authentication` with a nonce (SHA-256 hex to Apple, raw value to the server). Every Apple token from a device is verified against Apple's published keys (issuer, the app as audience, expiry, nonce) before anything reads it, because unlike the web's it never passed through Apple's token endpoint. It is finished through grnyte's server so the auto-link, conflict and contested-sign-up rules apply as on web. "Confirm with Apple" works natively on iOS for every re-auth action, bound to the linked Apple `sub` and a server-issued nonce for that action and target that lives 5 minutes, and revokes the app's Apple authorization when it confirms deletion or removing Apple, only after the Apple ID matched and only for an authorization code of that same Apple ID. Android has no native "Confirm with Apple": Apple-linked accounts there confirm by code, and their deletion records a skipped revocation.
- **Universal links.** `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` for content deep links (an explicit list, `/areas`, `/blocks`, `/routes`, `/feed`, `/users`; never `/auth`, `/api`, `/explore`, `/profile`, `/invite`, settings or region account screens), each file off until its own app-specific setting is set (`IOS_APP_ASSOCIATION_ENABLED` for Apple, `ANDROID_CERT_SHA256` for Android); the Apple file's `webcredentials` names only the app and exists for the iOS sign-in return. grnyte builds no passkey or shared-credential feature on it, though iOS may offer saved grnyte passwords in the app.
- **Web sign-ins end on an unclaimed page.** Every web sign-in or sign-up flow that ends by sending the browser to a `next` destination (password sign-in, code confirmation, the profile step, the OAuth provider return, invite accept after sign-in) ends on a new page `/auth/continue?next=<path>` under the excluded `/auth`, which validates `next` with the existing same-origin check and moves there with a client-side `location.replace` (a plain link without JavaScript). A redirect at the end of a chain that started on another site (Google, Apple) could otherwise open the installed app on a claimed content path mid-flow while the session stays in the browser; an in-page navigation is not handed to an app.
- **Expo test app.** A throwaway app at `expo-auth-test/` in the repo, gitignored and never committed, with unstyled screens for every flow: email sign-in, create account with proof-of-work solved by `react-native-quick-crypto`, code entry with `textContentType="oneTimeCode"` / `autoComplete="one-time-code"`, Apple (native iOS, browser Android), Google (browser), profile step, sign-in methods with link and unlink, re-auth with "Confirm with Apple", deletion with Apple revocation, and sign out. Sessions use Supabase's React Native pattern: an AES key in `expo-secure-store`, the encrypted session in AsyncStorage. Proven on the iOS Simulator and an Android emulator. The test app is also the only proof of the spec's client contracts, which the server cannot verify.
- **Not breaking for web.** No URL changes, no remote file moves, no export renames, no `manifest.id` change. Handler bodies move out of remote functions into server modules the remote functions still call, under the same export names. Already-loaded tabs see nothing new.
- **A new permanent contract.** Installed native apps cannot be reloaded the way a tab can, so `/api/app/v1/*` request and response shapes only widen, forever within `v1`, except for the three fixed answers above, which keep closing a channel, forcing an update and retiring `v1` possible.

## Non-goals

- The real native app, its design, navigation, Zero client and store release. The test app proves auth and is thrown away.
- The own OAuth client, `/auth/callback/<provider>`, the carrier list and web carrier, the sealing helper, Apple client-secret minting, Apple revocation, auto-link and conflict rules, the sign-in methods section and web "Confirm with Apple": all `add-social-sign-in`. This change adds one carrier and calls the rest, it does not redefine them.
- Codes, re-auth grants, the `auth.identities` trigger, session liveness, the profile step and the auth event log: all `harden-auth-codes`.
- An https sign-in return on Android (a Chrome Auth Tab module is a follow-up for the native project), passkeys or any shared-credential feature, Google's paid native module, App Attest or Play Integrity.
- Invitations in the app: the `regions.acceptInvitation` Zero mutator takes an `invitationFk`, not the mailed token, and nothing here resolves a token, so the app can neither show nor accept an invitation link yet; `/invite` is not claimed by the link files and no `v1` shape is frozen for it. The native project adds both together.
- Native push, deep-link routing inside the app, and the installed-PWA return screen.

## Capabilities

### New Capabilities

- `auth/app-api`: how a native client reaches grnyte's server-owned auth steps: the endpoint set, Bearer-only authentication with session liveness, no cookies, no CORS, JSON-only bodies, parity with the web handlers, and the widen-only contract.
- `auth/native-handoff`: the app-started browser sign-in and link: PKCE challenge registered at start, the server-held transaction, the return to the app (https on iOS, the private-use scheme on Android) with a 60-second single-use code, the exchange, and the no-web-cookies rule.
- `auth/native-sign-in`: native Apple sign-in on iOS with its nonce rule, native "Confirm with Apple" for re-auth and revocation, and the client contracts (session storage, password normalisation, proof-of-work, code autofill) only the test app can prove.
- `auth/app-links`: the universal-link and app-link files: what they claim, what they never claim, and how they are served; the `webcredentials` section for the iOS sign-in return; and the unclaimed `/auth/continue` page every web sign-in with a destination ends on.

### Modified Capabilities

None. The specs this change leans on (`auth/reauthentication`, `auth/sessions`, `auth/auth-events`, `auth/profile-completion` and `add-social-sign-in`'s) are new in the two sibling changes and not yet archived; this change adds its own requirements beside them instead of editing them.

## Impact

- **Routes (new)**: `src/routes/api/app/v1/**/+server.ts` (one per step, `oauth/start` and `oauth/exchange` included, listed in design.md), `src/routes/.well-known/apple-app-site-association/+server.ts`, `src/routes/.well-known/assetlinks.json/+server.ts`, the sign-in end page `src/routes/(landing)/auth/continue/` (a new permanent URL, `/auth/continue`, with a plain link and its `auth_continue*` keys in `messages/en.json` and `messages/de.json`), and the iOS return page `src/routes/(landing)/app-return/` (a new permanent URL, `/app-return`, with two short sentences telling the person to go back to the grnyte app and a plain link to grnyte, in `messages/en.json` and `messages/de.json`). No callback route: app flows return through `add-social-sign-in`'s `/auth/callback/<provider>`. The proof-of-work challenge gets a versioned alias, `GET /api/app/v1/challenge`, over the same `issueChallenge`; the web's `/auth/challenge` stays as it is.
- **Hook**: `src/lib/hooks/auth.server.ts` (Bearer path on change 1's `APP_API_PREFIX`, matched on the request's own URL; `getPageState` exported; `/.well-known/` public; `/auth/continue` joins `AUTH_PASSTHROUGH_PATHS`). `crossSite.server.ts` unchanged (change 1 already exempts the prefix). `src/lib/hooks/rate-limit.server.ts` keeps its in-memory per-IP limit on the prefix as best effort only, answering its 429 there as JSON; every start is bounded by a per-client cap on the flow table itself.
- **Shared code (new)**: `src/lib/auth/app/` (`endpoint.server.ts` wrapper, `v1.ts` request and response shapes with a contract test, `bearer.server.ts`, `handoff.server.ts` with the app carrier, `appleToken.server.ts`, `appleReauth.server.ts`, `association.server.ts` with both link files, `constants.ts` with `APP_LINK_PREFIXES`); `$lib/auth/index.ts`'s `signedInRedirectTarget` answers `/auth/continue?next=` for a valid `next`, and `auth/confirm/+server.ts` sends its success redirects through it; `add-social-sign-in`'s `carriers` gains the app carrier at its front. Shared helpers lifted, behaviour unchanged: `parseBearer` (`verify.server.ts`; `zeroCaller` keeps its own parsing), `taggingJwks` and `JwksUnavailable` (`verify.server.ts`), `sha256hex` (exported by change 2 beside `providerNonce`), `kitRefusal` (`serverMutator.server.ts`), and change 2's `confirm`-intent validation if it is inline.
- **Docs**: AGENTS.md's deploy-skew list gains the widen-only rule for `/api/app/v1`, and its Conventions gain that every new server-owned auth step also gets an app endpoint.
- **Remote functions touched, names kept**: `signup.remote.ts`, `signin.remote.ts`, `forgot-password.remote.ts`, `profile.remote.ts`, `settings/account.remote.ts`, `lib/auth/reauth.remote.ts`, `lib/auth/session.remote.ts` and `add-social-sign-in`'s link and unlink exports: bodies that still live inside a remote function move to a `*.server.ts` beside it.
- **Entity modules**: `user` (`delete.server.ts`, `provision.server.ts`, called).
- **Tables**: new `app_auth_flows` (migration `0150`, RLS on, no policies, no `authenticated` access, not in the Zero schema; its rows replicate into zero-cache like every public table, holding only hashes and sealed values); reads `auth.identities`, `auth.sessions` through change 1's helpers; `auth_events` gains kind `handoff_failed`.
- **Configuration**: GoTrue's Apple client ID list gains the bundle ID `rocks.grnyte` (the second local stack, prod, asserted by `check:prod`); no new production return URL, but the ngrok Google callback is registered for local testing; new env `ANDROID_CERT_SHA256`, `IOS_APP_ASSOCIATION_ENABLED` and `APP_MIN_VERSION`, all unset in prod until a native app ships (`APPLE_TEAM_ID` comes from change 2); `.gitignore` gains `/expo-auth-test/`; `.fallowrc.jsonc` ignores it.
- **Dependencies**: no new package for the web app. Builds on `migrate-supabase-keys`, `harden-auth-codes` and `add-social-sign-in`; its app-API twins call their handler bodies, so they need no `supabaseAuthServer` method beyond the ones those changes add (`verifyOtp`, `resetPasswordForEmail`, `resend`, `signInWithPassword`, `signInWithIdToken`), and on `supabaseAuthServerAs`, which the app path uses for every call that acts as the person (link, email change, sign out other devices, sign-in methods, unlink), so this change widens its `AuthServerAs` by `signOut`, `getUserIdentities` and `unlinkIdentity`; the password sign-in and its unconfirmed branch go through `supabaseAuthServer` as on the web. Decided: it stays off develop until the key-migration runbook has passed its step 5. The test app's own `package.json` (Expo SDK, `expo-apple-authentication`, `expo-web-browser`, `expo-secure-store`, `@react-native-async-storage/async-storage`, `aes-js`, `react-native-quick-crypto`, `@supabase/supabase-js`) is never committed.
- **Outside setup**: Apple Developer Program paid for the App ID `rocks.grnyte` with Sign in with Apple and Associated Domains, made the primary App ID of `add-social-sign-in`'s Services ID (regrouped and its key re-issued if it already sits under another) so its one `.p8` key also mints client secrets for the bundle ID; ngrok static domain as the test app's origin.

## Resolved assumptions

The one home for these rulings; design, specs and tasks point here. Each was a choice the earlier social-login rulings did not cover, or a place where a later ruling changed an earlier one; the user ruled on all of them (2026-11-09), and plan review round 1 refined some (noted).

1. **Code verification goes through endpoints**; the app calls GoTrue directly only for password sign-in, token refresh and sign-out (refines how the app reaches server auth steps). (`auth/app-api`)
2. **Native Apple sign-in finishes on grnyte's server** through `add-social-sign-in`'s `dispatchIntent` (refines the browser flow for Google in the app). (`auth/native-sign-in`)
3. **Replaced:** app-started flows return through the web's `/auth/callback/<provider>` and plug into `add-social-sign-in`'s carrier model as an app carrier, looked up by `hash(state)` in this change's server table, setting no cookie, landing on the app's return (round 1: `/app-return` over https on iOS, `rocks.grnyte:/auth` on Android); no second provider return URL is registered. (`auth/native-handoff`)
4. **Changed:** the handoff row holds the provider's `VerifiedProof` (ID token, raw nonce, claims) and the transaction (with the provider PKCE verifier) sealed with `add-social-sign-in`'s sealing helper under a key derived from `SUPABASE_SECRET_KEY`; no client can query the table and there is no `authenticated` access (its rows do replicate into zero-cache, sealed and hashed). No grnyte session is ever at rest. (`auth/native-handoff`)
5. **The handoff code is 32 random bytes stored as a SHA-256 hash**, spent before the PKCE comparison, as written. (`auth/native-handoff`)
6. **An app link records the starting account and session**; the exchange needs a Bearer token for the same pair, and the start needs an `identity.link` grant, as written. (`auth/native-handoff`)
7. **Native "Confirm with Apple" nonces are server-issued and stored** in the same table (round 2: only their digest), bound to account, session, action and target, single use, 5 minutes. (`auth/native-sign-in`)
8. **Native Apple revocation uses the sign-in's authorization code** with the bundle ID as `client_id`, at confirmation (round 2: after the Apple ID matched the account, so after the grant, and only when Apple's answer to the code names that same Apple ID). (`auth/native-sign-in`)
9. **Link-file scope** (restored 2026-11-15 by the user, undoing that day's content-link cut): Apple excludes `/auth/*` and `/api/*` first, then claims the same explicit content paths Android's intent filters list (refined in rounds 1 to 3: never `/*`, `/explore`, `/profile`, `/invite`, settings or region account screens); the Apple file answers 404 until `IOS_APP_ASSOCIATION_ENABLED` is set, the Android file until `ANDROID_CERT_SHA256` is. Every web sign-in with a `next` ends on the unclaimed `/auth/continue` (design decision 12). (`auth/app-links`)
10. **`/.well-known/` becomes a public prefix in the hook**, as written. (`auth/app-links`)
11. **`vercel.json` stays as is**; tests assert no `Access-Control-Allow-Origin`, as written. (`auth/app-api`)
12. **A Bearer request never refreshes**, as written. (`auth/app-api`)
13. **A Bearer caller without a profile gets `profile_required`** except on the profile step, re-auth, new password, sign out other devices and deletion, as written. (`auth/app-api`)
14. **Handoff errors return as `?error=cancelled|expired|failed`** on the flow's own return, from the app carrier's `land`. (`auth/native-handoff`)
15. **Handoff failures are `handoff_failed`** (refined in round 1) only where nothing else records them: `state_replayed`, `code_unknown`, `pkce_mismatch`, `link_caller_mismatch`, `apple_reauth_mismatch`, `apple_token_invalid`, `apple_code_mismatch`; the shared callback's own refusals stay change 2's `oauth_*` events. (`auth/native-handoff`, `auth/native-sign-in`)
16. **No new rate limiter, but a per-address start cap** (round 2): the in-memory per-IP limit is best effort; a start (anonymous or Bearer, refined in round 5) is refused when its client (IPv4 address or IPv6 /64, stored only as an HMAC) already holds 10 open flows; a slight overshoot under concurrency and the shared-address lockout are accepted (round 3). Rows are swept an hour after they expire and survive a successful exchange, so a late return still reaches the app as `expired` and a replay is recognised. (`auth/app-api`, `auth/native-handoff`)
17. **The test app is a development build** reaching grnyte through the reserved ngrok static domain in front of a built server, and the second local stack's GoTrue directly on the host (refined in round 1).
18. **The bundle ID joins GoTrue's Apple client ID list in this change**; `add-social-sign-in` leaves it here, as written.
19. **`POST /api/app/v1/signin/unconfirmed` exists**: the right password on an unconfirmed account re-sends the code and opens code entry without flagging, through the same handler body as the web's unconfirmed sign-in branch in `harden-auth-codes`. On an account that turns out confirmed it ends the session GoTrue just opened and answers `alreadyConfirmed` (round 1). (`auth/app-api`)
20. **The app normalises a password to NFC before its direct GoTrue sign-in, with the web's one retry as entered**, as the web sign-in does on the server; to `signin/unconfirmed` it posts the password as entered, and the server applies the same rule. (`auth/native-sign-in`)

## Return-channel rulings

Round 1's ruling stands as built: iOS returns on an https URL iOS hands only to grnyte's app (`/app-return` with `preferUniversalLinks`, iOS 17.4, `applinks:` and `webcredentials:` associated domains); Android keeps `rocks.grnyte:/auth`; the app names its return channel at `oauth/start`; PKCE stays required on both. Round 2's two items were ruled by the user:

1. **Impersonation through the scheme channel is an accepted risk on both platforms** (review P39), as RFC 8252 accepts it; no User-Agent check; the iOS https return stays; app attestation is a follow-up for the real native project. The risk itself is stated once, in design.md's Risks.
2. **Native "Confirm with Apple" is iOS only** (review P50). An Apple-linked account on Android confirms by code, so a deletion or Apple removal from Android records `apple_revoke_skipped`; Apple's revocation requirement is an App Store rule that binds the iOS app only. A browser "Confirm with Apple" on Android through the handoff (a `confirm` purpose on `oauth/start`) is a follow-up. (`auth/native-sign-in`)
