# Design

## Context

See proposal.md for why. The state this design starts from, after `migrate-supabase-keys` (new API keys, asymmetric JWT signing keys, `supabaseAuthServer(event)`), `harden-auth-codes` (change 1) and `add-social-sign-in` (change 2) are applied:

- `src/hooks.server.ts` runs `sequence(crossSiteGuard, rateLimit, paraglide, supabase, authGuard)`. The `supabase` handle (`src/lib/hooks/auth.server.ts`) builds `locals.supabase` with `@supabase/ssr` over Kit's cookies and installs `safeGetSession`, which verifies the cookie's access token with `verifyAccessToken` (`src/lib/auth/server/verify.server.ts`, `jose`) and keeps the branded `VerifiedToken` on `locals.verifiedToken` beside `locals.claims` (change 1). `verifyAccessToken` answers `unavailable` for a JWKS outage, which the hook turns into `backendUnavailable` rather than a sign-out (`migrate-supabase-keys`). `getPageState` is a closure inside the `supabase` handle. Change 1's `isSessionLive` / `requireLiveSession` (`src/lib/auth/server/session.server.ts`) run on auth, account and admin actions and every synced write, and name the app API as one more place; a failed liveness read throws and becomes 503 `auth_serviceUnavailable`, never a sign-out. Nothing reads `Authorization` except the Zero endpoints, through `zeroCaller` (`src/lib/zero/caller.server.ts`), which parses the header loosely with `.replace('Bearer ', '')`. Change 1 exports `APP_API_PREFIX = '/api/app/'` from `auth.server.ts`, exempts it from `crossSiteGuard`, and makes `authGuard` cookie-blind there (anonymous locals, like `ZERO_API_PREFIX`). `rateLimit` (500 requests per IP per 15 minutes) still applies to the prefix.
- `/api/` is a public prefix in `authGuard`; `/.well-known/` is not, so an anonymous fetch there is answered 303 to `/auth`.
- Kit's default CSRF check refuses a cross-origin `POST` with a form content type (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`), and also one with no `Origin` header, outside dev. It lets `application/json` through.
- `vercel.json` adds `Access-Control-Allow-Credentials: true` to every path and `Access-Control-Allow-Origin` only to image files.
- Server-owned auth steps are remote functions. Change 1's bodies: `signUp` (returns a resend token), `confirmSignupCode`, `resendSignupCode` (`signup.remote.ts`), the unconfirmed branch of `signIn` (`signin.remote.ts`, `email_not_confirmed` after GoTrue checked the password), the forgot-password request and `confirmResetCode` (`forgot-password.remote.ts`), `setNewPassword`, `completeProfile` (`auth/profile/profile.remote.ts`), `changeEmail` (through `supabaseAuthServerAs(event, locals.verifiedToken)`) / `confirmEmailChangeCode` (after the second code: `voidReauth`, `refreshSession()`, `signOut({ scope: 'others' })` on `locals.supabase`) / `changePassword` / `deleteAccountCommand` / `accountDeletionPreview` (`settings/account.remote.ts`), `requestReauthCode` / `confirmReauthCode` / `reauthGrantStatus` (`src/lib/auth/reauth/reauth.remote.ts`), `signOutOthers` (`src/lib/auth/session.remote.ts`, no re-authentication). Change 2 adds `signInMethodsQuery` and `unlinkProvider` (`src/lib/auth/methods/identities.remote.ts`) and the own OAuth client. Invitation acceptance is the `regions.acceptInvitation` Zero mutator, which takes an `invitationFk`, not the mailed token; nothing here reads or accepts invitations, so the app cannot handle an invitation link yet and no `v1` shape is frozen for one.
- Change 1's `supabaseAuthServerAs` (`src/lib/auth/server/authServer.server.ts`) seeds a fresh in-memory storage with a `VerifiedToken` (`persistSession: true`, explicit `storageKey`, far-future `expires_at`, empty refresh token) so auth-js acts as the person. Its `AuthServerAs` allows `linkIdentity` and `updateUser`; change 2 keeps `getUserIdentities`, `unlinkIdentity` and `signOut({ scope: 'others' })` on `locals.supabase`.
- `src/lib/zero/serverMutator.server.ts` already turns Kit's `error()` and `invalid()` into another transport's error (`isHttpError`, `isValidationError`).
- The proof-of-work challenge is `GET /auth/challenge` (`issueChallenge`, ALTCHA PBKDF2); `screenSubmit` spends a solution.
- The newest migration on develop is `0147`; change 1 adds `0148` (tables) and `0149` (guards); change 2 adds none. This change's table is `0150`.
- Zero's publication covers schema `public`, so every table there replicates into zero-cache's replica; only tables in the Zero schema are queryable by a client.

### What this design uses from `add-social-sign-in`

Change 2's design (decisions 1 to 7 and 13) defines the carrier model this change plugs into. In `src/lib/auth/oauth/`, used as they are:

1. `providers.server.ts`: `OAuthProvider`, `configuredProviders(event)` (env complete and the request origin equal to `PUBLIC_ORIGIN`), `redirectUri(provider)` (`${PUBLIC_ORIGIN}/auth/callback/${provider}`), `appleClientSecret(clientId)`, `revokeAppleToken(refreshToken, clientId): Promise<boolean>`.
2. `transaction.server.ts`: `OAuthTransaction { carrier, provider, intent, state, nonce, codeVerifier, next, returnTo, startedAt }` (`carrier` widened here to `'web' | 'app'`, the one change 2 announces), `VerifiedProof { idToken, rawNonce, claims, refreshToken? }`, `CallbackResult`, `TransactionCarrier { take(event, state), land(event, tx, result) }` and the `carriers` list, where change 2 reserves the first place for this change's carrier.
3. `flow.server.ts`: `OAuthIntent`, `buildAuthorizationUrl(provider, tx)`, `completeOAuth(event, provider)` behind change 2's unchanged `/auth/callback/apple` (Apple's `form_post`, answered 303 to a same-origin GET) and `/auth/callback/google`. It asks the carriers in order, checks state, age (10 minutes, recording `oauth_state_mismatch` on failure) and provider, runs the code grant with nonce, issuer and audience checks (recording `oauth_nonce_mismatch` / `oauth_iss_mismatch`), then calls the carrier's `land`. `dispatchIntent(ctx: DispatchContext { event, authServer, verifiedToken? }, tx, proof)`: `decideSignIn`, the contested take-over and `signInWithIdToken` for `signin`; the caller match, grant peek, `decideLink`, `bindLinkGrant`, `linkIdentity` and the sign-out of the link's throwaway session for `link`. It writes no session; the carrier hands the `signedIn` outcome's session out. On `/auth/callback/*` the hook loads no session before a carrier is known.
4. `seal.server.ts`: `seal(info, value)` / `unseal(info, sealed)`, JWE under change 1's `labelledKey('seal:' + info)`.
5. `linking.server.ts`: `acceptAppleConfirmation(caller, action, target, claims)`, which checks the caller's session against the transaction's and the token's `sub` against the caller's linked Apple identity (`oauth_sub_mismatch`), then writes the `apple` grant. It applies no age rule (change 2 accepts that Apple's web `iat` is the exchange moment). It does not verify the token: on the web the token came from Apple's token endpoint over TLS.
6. `providerNonce(raw)`, the one place the provider's nonce digest is computed, and `sha256hex(value)`, exported beside it, which this change also uses for `state_hash` and `code_hash`.
7. The `confirm`-intent validation inside `startOAuth`: a valid `ReauthAction`, a target of that action's shape, a bare provider for `identity.*`.

Departures from change 2's design, stated so the two stay readable side by side:

- Change 2's contract for this change says the app carrier redirects to `rocks.grnyte:/auth`. Here it redirects to the flow's own return (decision 4): an https return on iOS, the scheme on Android.
- `TransactionCarrier.take` returns a transaction or null in change 2. The app carrier's `take` may also end the request itself, by throwing the redirect its `land` would send, for a state it owns but must not serve (a replay, decision 4). `completeOAuth` must let that throw through and must not run the code grant; task 2.1a's stub carrier pins it.

## Goals / Non-Goals

**Goals:**

- One handler body per auth step, reached by the web through its remote function and by the app through its endpoint.
- Bearer handling confined to one prefix by construction: the cookie path never reads `Authorization`, the Bearer path never touches `event.cookies`.
- The handoff reuses change 2's OAuth client end to end, callbacks included; it differs only in where the transaction lives and how the result is delivered.
- Every Apple ID token that reaches the server from a device is verified against Apple's keys before any of its claims is read.

**Non-Goals:** see proposal.md. Also: no Zero query, no Zero mutator, no Zero schema change, no new remote function, no new callback route. Every endpoint is a plain `+server.ts`, because a native client can call neither a remote function nor (yet) Zero. No change to `get-queries` or `mutate` authentication.

## Decisions

### 1. One prefix, built by one wrapper, with its own shapes

Every app endpoint lives under `src/routes/api/app/v1/` and is built by `appEndpoint` in new `src/lib/auth/app/endpoint.server.ts`:

```ts
export function appEndpoint<Req, Res>(options: {
  auth: 'bearer' | 'none'          // 'none' still reads a Bearer if present, for optional callers
  profile?: 'optional' | 'required' // default 'required' when auth is 'bearer'
  request: V1Schema<Req>            // this endpoint's own v1 shape, from src/lib/auth/app/v1.ts
  handler: (input: Req) => Promise<Res> // Res is z.infer of the endpoint's v1 response shape
}): RequestHandler
```

Responses are typed against their `v1` shape but not parsed at runtime; the endpoint tests parse every response with it.

Every refusal under the prefix is JSON with `cache-control: no-store`, shaped in `v1.ts` (`{ error: { code } }` for 401 `auth_sessionEnded`, 415 `unsupported_media_type` and 429 `auth_rateLimited`, the existing key; `rateLimit` answers its 429 in that shape on `APP_API_PREFIX` instead of plain text). In order: `POST` must carry `Content-Type: application/json` (415 otherwise, before reading the body; `GET` endpoints take query parameters and no body); `X-App-Version` below `APP_MIN_VERSION` answers `400 { error: { code: 'app_update_required', minVersion } }`, before anything that reads the token or the body, so an old build with an expired token or an old body shape still learns it must update; `locals.backendUnavailable` answers `503 { error: { code: 'auth_serviceUnavailable' } }` (a JWKS outage or a failed session read is not a sign-out, decision 2); parse with the `v1` request schema (400 with `{ error: { code: 'invalid_request', field } }`); for `bearer`, `locals.claims == null` answers 401; `profile: 'required'` and `locals.user == null` answers `403 { error: { code: 'profile_required' } }`; run the handler; answer `json(result, { headers: { 'cache-control': 'no-store' } })`. Kit's `error()` and `invalid()` thrown from a shared body are translated by an exported `kitRefusal(e): { status, message, field } | undefined`, lifted from `serverMutator.server.ts`'s `run` and called by both (no second copy, `lint:duplication`). On the app path every error then has one shape, `{ error: { code, params?, field? } }`: `appEndpoint` decodes a `formError` marker (a `message` holding the web's JSON-encoded `{ message, params }`) into `code` and `params`, so the app never sees the web's encoding and a later change to `formError` cannot reach the frozen contract.

The `v1` schemas are this change's own, not the web remote functions'. They own the SHAPE (field names, types, which are required), which only widens; the shared body still applies every VALUE rule (the password policy, the username rules) through the same leaf validators the web uses, so a stricter rule reaches the app at once while a reshaped web form never narrows `v1`. A contract test (`src/lib/auth/app/v1.contract.test.ts`) renders each request and response schema as JSON Schema (`z.toJSONSchema`) and diffs it against a committed file, `src/lib/auth/app/v1.contract.json`: a removed or tightened property (a removed field, a field made required, a narrowed type or enum) fails, an added optional field passes and is committed. Such a failure is a `v2`, never an update of the file.

Three answers are outside the widen-only rule, because without them a channel could never be closed or hardened. Each has one fixed error shape every app build must handle from its first release: a refusal for a security reason on any endpoint (`403 { error: { code: 'refused_for_security', message } }`, for example once the scheme return is closed; `message` is a fixed text per cause, never anything account-specific); `400 { error: { code: 'app_update_required', minVersion } }` when the app's version is below the minimum (400 rather than 426, which would require an `Upgrade` header that means nothing here); and `410 { error: { code: 'api_version_retired' } }` for every `v1` endpoint once `v1` is sunset. The test app shows each as plain text. Nothing in this change sends `refused_for_security` or `api_version_retired`: no condition triggers them yet, only their shapes in `v1.ts` and the test app's handling ship, so a later release can. Every error answer and refusal, like every success, carries `cache-control: no-store`.

The app version. Every app build sends `X-App-Version: MAJOR.MINOR.PATCH` (three non-negative integers, compared numerically in that order) on every call from its first release; the test app's `lib/api.ts` sends it. The minimum lives in one env var, `APP_MIN_VERSION`, in the same format. Unset means no minimum and nothing is refused; once set, a missing or unparseable header counts as below it. This is a compatibility lever to retire old builds, never a security control: a header is whatever the caller says, so closing a channel or refusing a client is done server-side with `refused_for_security`.

`OPTIONS` is never exported, so Kit answers 405 with no CORS headers. `vercel.json` is left alone (resolved assumption 11).

Change 1's `crossSiteGuard` exempts `APP_API_PREFIX`, matched on `event.request.url`: `authGuard` never reads a cookie session on this prefix (decision 2), so there is nothing for a cross-site request to ride on, and the JSON-only rule above refuses a `text/plain` or form post before any handler runs. `rateLimit` is not exempt, but its counter lives in one server instance's memory, so on Vercel it is best effort only. The real bound on `oauth/start` inserts is decision 4's per-client cap.

Rejected: one dispatcher route keyed by step name (one URL forever, but every step's auth and schema then lives in a table instead of beside its route); reusing `authedCommand`'s `run` (it is built around `command()` and `getRequestEvent` inside a remote call); reusing the web schemas (a web-side reshape would silently narrow the frozen contract).

### 2. The Bearer path in the hook

The prefix is matched on `new URL(event.request.url).pathname`, in both the `supabase` handle and `authGuard`, never on `event.url`: Kit rewrites `event.url` from `x-sveltekit-pathname` for a remote-function call, so a remote call could otherwise claim to be under `/api/app/`. For a path under change 1's `APP_API_PREFIX`, before the cookie client is built, the `supabase` handle installs:

- No user-scoped client of its own: `locals.supabase` on the prefix is an anonymous supabase-js client (publishable key, `persistSession: false`, no storage), so a stray call acts as nobody. Every call that acts as the person goes through change 1's `supabaseAuthServerAs(event, locals.verifiedToken)`, the one user-scoped client, on both transports: the shared bodies of `signOutOthers`, `confirmEmailChangeCode` and `unlinkProvider` (`signOut({ scope: 'others' })`), `signInMethodsQuery` (`getUserIdentities`) and `unlinkProvider` (`unlinkIdentity`) switch from `locals.supabase` to it when task group 3 moves them, and `AuthServerAs` widens by `signOut`, `getUserIdentities` and `unlinkIdentity`. On the web the switch changes nothing visible: those calls need only the access token, and the cookie session they used to run on is the same session. GoTrue code calls and password sign-ins go through `supabaseAuthServer(event)` as before (the lifted `signin.server.ts` body calls `signInWithPassword` there and returns the session: the web branch writes it with `setSession`, the app branch ends it with `admin.signOut`), so GoTrue's per-IP limits see the app user's own address. The web's `refreshSession()` after an email change stays on the cookie client (decision 3).
- `locals.safeGetSession = () => bearerSession(event.request)`: `parseBearer(request)` (new export of `verify.server.ts`: exactly `Authorization: Bearer <token>`, scheme case-insensitive, one token, else nothing; `zeroCaller` keeps its own parsing, untouched), `verifyAccessToken`, never refresh (resolved assumption 12), `isSessionLive(db, claims)` (change 1), then `getPageState` (lifted out of the `supabase` handle's closure into a module export, unchanged). It returns the claims AND the branded `VerifiedToken`, and the hook sets both `locals.claims` and `locals.verifiedToken`, because change 1's email change hands `locals.verifiedToken` to `supabaseAuthServerAs` and change 2's `dispatchIntent` reads `ctx.verifiedToken`. A missing, invalid or expired token, or a dead session, is anonymous; no sign-out call, since there is nothing to clear. `unavailable` from `verifyAccessToken`, a thrown `isSessionLive` read and a failed `getPageState` all set `backendUnavailable: true` with anonymous locals, which `appEndpoint` answers as 503 JSON, never 401 and never a hook 500.

`authGuard` keeps change 1's `APP_API_PREFIX` branch (no cookie claims, returns before the bounces) and fills it from the Bearer `safeGetSession` above instead of fixed anonymous locals, so on this prefix the Bearer header is the only session source and a web cookie is never one. That cookie blindness is what makes change 1's cross-site exemption of the prefix safe, so the branch must never fall back to the cookie client. The cookie path elsewhere is untouched and never reads `Authorization`, which is what makes "Bearer counts nowhere else" true by construction; a hook test pins both directions.

No `Set-Cookie` can come from this path because nothing on it calls `event.cookies` and no client on it writes them. A server test asserts the header is absent on every endpoint, enumerated from the `+server.ts` files under `src/routes/api/app/v1/`, including with near-expiry web cookies attached, rather than stripping it after the fact.

Rejected: accepting Bearer on every route; building the cookie client and ignoring it on this prefix (`getSession()` could rotate a web refresh token onto a response the app never stores, the same reason `ZERO_API_PREFIX` skips it); a Bearer client of its own over seeded storage (a second user-scoped client beside `supabaseAuthServerAs`, and a second copy of its seeding).

### 3. Shared handler bodies

The rule: the remote function and the endpoint call one exported function in a `*.server.ts` beside the remote file, which reads its caller through `getRequestEvent().locals` (populated identically on both paths) and returns a value both can use. Bodies that sign in return the session they got from GoTrue; the remote function writes it as it does today, the endpoint returns `{ session: { access_token, refresh_token, expires_at } }`. Where change 1 or 2 already keeps the body in a `*.server.ts`, the endpoint calls it directly; where it lives inline in a remote file, task group 3 moves it out first, unchanged, keeping every export name (no deploy skew, AGENTS.md). Two bodies get an explicit transport branch instead of moving unchanged (below).

| Endpoint (`/api/app/v1/...`) | Auth | Body | Returns |
| --- | --- | --- | --- |
| `GET challenge` | none | `issueChallenge` | challenge |
| `POST signup` | none | `signUp` body | `{ ok, resendToken }` |
| `POST signup/confirm` | none | `confirmSignupCode` | `{ next, session }` |
| `POST signup/resend` | none | `resendSignupCode` (takes `resendToken`) | `{ ok }` |
| `POST signin/unconfirmed` | none | `signIn`'s unconfirmed branch | `{ confirm, resendToken }`, `{ alreadyConfirmed: true }` or the generic failure |
| `POST password/forgot` | none | forgot-password request | `{ ok }` |
| `POST password/reset/confirm` | none | `confirmResetCode` | `{ session }` |
| `POST password/new` | bearer, profile optional | `setNewPassword` | `{ ok }` |
| `POST password/change` | bearer | `changePassword` | `{ session }` |
| `POST profile` | bearer, profile optional | `completeProfile` | `{ ok }` |
| `POST email/change` | bearer | `changeEmail` | `{ sentAt, expiresAt }` |
| `POST email/confirm` | bearer | `confirmEmailChangeCode` with `{ refresh: false }` | `{ next }`, then `{ next: 'done', session }` |
| `POST reauth/request`, `reauth/confirm` | bearer, profile optional | `requestReauthCode`, `confirmReauthCode` | as web |
| `GET reauth/status` | bearer, profile optional | `reauthGrantStatus` | `{ confirmed }` |
| `POST reauth/apple/start`, `reauth/apple/confirm` | bearer, profile optional | decision 6 | decision 6 |
| `GET account/deletion-preview` | bearer, profile optional | `accountDeletionPreview` body | blockers |
| `POST account/delete` | bearer, profile optional | `deleteAccount` | `{ ok }` |
| `GET sign-in-methods` | bearer | `signInMethodsQuery` body | methods |
| `POST identities/unlink` | bearer | `unlinkProvider` body | `{ ok }` |
| `POST identities/link/apple` | bearer | decision 5 | `{ ok }` |
| `POST sessions/sign-out-others` | bearer, profile optional | `signOutOthers` (no re-authentication) | `{ ok }` |
| `POST oauth/start`, `oauth/exchange` | none or bearer | decision 4 | decision 4 |
| `POST oauth/apple/native` | none | decision 5 | `{ session }` or refusal |

`GET challenge` is a versioned alias over `issueChallenge`, so every native call stays inside the frozen prefix and the app is not tied to the web's `/auth/challenge`, which stays as it is for the web.

`signup/confirm`, `password/reset/confirm` and `email/confirm` call change 1's handler bodies, so they inherit its per-address try count: a 6th try at a code answers `auth_codeLocked` without reaching GoTrue, and the matching resend endpoint clears it. The app's code fields take 8 digits for these and 6 for `reauth/confirm`.

`signin/unconfirmed` exists because the app signs in with a password directly at GoTrue (resolved assumption 1), and GoTrue's `email_not_confirmed` leaves it no way to get a fresh code without flagging the account; the endpoint runs change 1's unconfirmed branch (password checked by GoTrue, resend without flagging, the password normalised to NFC first and retried once as entered), so the app posts the password exactly as entered, never its normalised form, or the server's retry could never fire; so the app behaves as the web does (resolved assumption 19). When the account turns out to be confirmed, GoTrue's sign-in succeeds and opens a session nobody would hold: the shared body's app branch ends it at once with `supabaseAdmin().auth.admin.signOut(accessToken, 'local')` (as change 2 does after a link) and answers `{ alreadyConfirmed: true }`, so the app signs in directly; the web branch keeps that session as today.

`confirmEmailChangeCode` gets a transport branch. GoTrue's verify of the second code answers a new session; after it the body runs `voidReauth`, then signs every other session out as that new session (`supabaseAuthServerAs` over its verified access token; as the caller's token if it does not verify, ending both). The remote function (`{ refresh: true }`) then writes the new session into its cookie client and answers `{ step: 'done' }`; the endpoint (`{ refresh: false }`) gets the session back and answers it, so the app replaces its own, which that sign-out ended (no refresh at GoTrue, resolved assumption 12). Every multi-step app answer uses one name: the endpoint maps the body's `step` to `next` (`{ next: 'next' }` after the first code, `{ next: 'done', session }` after the second).

A ratchet beside `src/lib/remote/gates.test.ts`: every `+server.ts` under `src/routes/api/app/` exports only handlers made by `appEndpoint`. Together with one parity case per endpoint (the same input through the remote function and the endpoint gives the same answer key and the same database change), that is what proves an endpoint runs the shared body; no endpoint test asserts separately that it does not call GoTrue itself.

### 4. The app-started browser flow: an app carrier

New `src/lib/auth/app/handoff.server.ts` over one new table (decision 7). It adds `appCarrier` at the front of change 2's `carriers`; nothing in change 2's start, callback or matching code is edited.

**Return channels.** Where the browser hands the result back depends on the platform, and the app says which at the start. `APP_RETURNS` in `constants.ts` is the allowlist, nothing else is accepted:

- `ios`: `${PUBLIC_ORIGIN}${APP_RETURN_PATH}` with `APP_RETURN_PATH = '/app-return'`, an https URL whose auth-session callback iOS hands only to the app the association file's `webcredentials` names. The app opens the flow with `openAuthSessionAsync(authorizeUrl, returnUrl, { preferUniversalLinks: true })` (`expo-web-browser` 55.0.11 or later), which runs `ASWebAuthenticationSession` with an `.https(host:path:)` callback; that needs iOS 17.4 and the app's associated domains `applinks:` and `webcredentials:` for grnyte's host, which the association file confirms (decision 8). The channel protects grnyte's own app only: the server cannot tell which app asked for which channel (Risks). The path is outside `/auth` and `/api` on purpose: a return under the start or callback paths would be routed straight back into the app mid-flow.
- `android`: `APP_SCHEME_RETURN` (`rocks.grnyte:/auth`), the private-use scheme, opened with `openAuthSessionAsync(authorizeUrl, 'rocks.grnyte:/auth')`. A Chrome Auth Tab return on a verified https URL is a follow-up for the real native project.

**Start** `POST oauth/start { provider, purpose: 'signin' | 'link', returnChannel: 'ios' | 'android', codeChallenge, codeChallengeMethod: 'S256' }`. A provider missing from `configuredProviders(event)` is refused, as at change 2's start. A `returnChannel` outside `APP_RETURNS` is refused. `codeChallenge` must be 43 base64url characters; any other method is refused. Every start is refused (`429 { error: { code: 'auth_tooManyStarts' } }`) when its client already holds 10 unclaimed, unexpired rows, whether or not it carries a Bearer (a signed-in caller's own token must not lift the cap) and whatever its purpose, `reauth/apple/start`'s rows included; that count is one indexed read on the table it guards, so it holds across server instances, unlike the in-memory limiter. The client is `event.getClientAddress()` keyed as the full IPv4 address or the IPv6 /64 (one IPv6 host can rotate through its whole /64), stored only as `client_hash`, an HMAC under change 1's `labelledKey('app-start-client')`, so neither the table nor zero-cache's replica holds a reversible address. The count and the insert are not one transaction: two simultaneous starts can overshoot the cap by a row or two, which is accepted, since the cap bounds growth rather than counting exactly. Accepted too: everyone behind one shared address (carrier-grade NAT, a campus) shares the 10 open flows, so a burst there can refuse a real person for a few minutes; a flow that returns frees its slot at once. `link` requires a Bearer caller (`await reauthCaller()`, change 1) with a profile (`profile_required` otherwise, as every other link entry point) and `hasGrant(caller, 'identity.link', provider)`, else `auth_reauthRequired`. It builds an `OAuthTransaction` with `carrier: 'app'`, intent `{ kind: 'signin' }` or `{ kind: 'link', caller }`, fresh `state`, nonce and provider PKCE verifier, `next: null`, `returnTo: APP_RETURNS[returnChannel]` (the return URL itself, read only by the app carrier's `land`; the web carrier never sees an app transaction, and the sealed value cannot be edited) and `startedAt`, and inserts a row with `state_hash = sha256hex(state)`, the app's `code_challenge`, the transaction sealed with `seal('grnyte app handoff v1', tx)`, and for `link` the caller's `auth_user_fk` and `session_id`. It answers `{ authorizeUrl: buildAuthorizationUrl(provider, tx) }`, whose redirect is change 2's `redirectUri(provider)`, the same registered return URL the web uses. The app opens it as its return channel says.

**Callback** is change 2's `/auth/callback/<provider>`, unchanged. `appCarrier.take(event, state)`:

1. Claims its row in one statement: `UPDATE app_auth_flows SET claimed_at = now() WHERE state_hash = $1 AND claimed_at IS NULL AND purpose IN ('signin', 'link') RETURNING *`, and unseals the transaction. Expired rows are still claimed, so `completeOAuth`'s age check (which records `oauth_state_mismatch`) sends them to the app as `expired` instead of to the web error page. Rows are swept only an hour after `expires_at` (decision 7), so a late return still finds its row.
2. No row claimed: one read `SELECT ... WHERE state_hash = $1`. A row exists (already claimed, whether or not its code was since exchanged, because the exchange keeps the row, below), so this is a replay of an app flow: record `handoff_failed` (`state_replayed`) and THROW the redirect to the flow's return with `?error=expired`, read from the row's sealed `returnTo`. `take` never returns a transaction for a replay, so `completeOAuth` never runs the code grant for it (the departure from change 2's `take` contract stated above). No row at all: answer null with no side effect, so the web carrier is asked next; a state this table never held, or one swept an hour after it expired, is not an app flow.

`completeOAuth` then runs every check change 2 runs for the web, and calls `appCarrier.land`, which always redirects 303 to `tx.returnTo` (the https return on iOS, the scheme on Android):

- `cancelled`: `?error=cancelled`.
- `failed`: `?error=expired` or `?error=failed`. Nothing is recorded here: `completeOAuth` already recorded its own `oauth_*` event, so a second event would count one failure twice.
- `proof`: draw 32 random bytes, store `code_hash = sha256hex(code)`, `proof = seal('grnyte app handoff v1', verifiedProof)` (the whole `VerifiedProof`, claims included, minus Apple's `refreshToken`, which no app intent uses) and `expires_at = now() + 60 s` on the same row, and answer `?code=<base64url>`.

**The iOS return page.** `ASWebAuthenticationSession` catches the redirect to the https return before anything loads, so normally no page renders. If it ever does (the URL opened in a plain browser, a failed callback match), `src/routes/(landing)/app-return/+page.svelte` (no server load, `csr = false`) says in two short sentences to go back to the grnyte app, and that if it did not open, the sign-in did not finish and should be started again there. Below them, one plain link to grnyte (`/`, no query) gives a person stranded in Safari a way out; its label names grnyte, never the app, because a tap on a same-domain link stays in Safari and cannot open the app. The page never reads the query, so neither its markup nor any script (the shell's own inline scripts included) carries the code, and the hook answers it with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. `/app-return` joins `PUBLIC_PREFIXES` and is exempt from change 1's profile gate. It is a permanent URL: installed apps return to it.

The callback never touches `event.cookies` on this path: the hook loads no session on `/auth/callback/*` before a carrier is known (change 2), Apple's POST bounce sets no cookie, and `appCarrier.land` sets none. A test drives a callback carrying near-expiry web session cookies and asserts no `Set-Cookie`.

**Exchange** `POST oauth/exchange { code, codeVerifier }`, Bearer optional. One statement spends the code and empties the row, keeping it: `UPDATE app_auth_flows SET code_hash = NULL, proof = NULL WHERE code_hash = $1 AND expires_at > now() RETURNING *` (the proof read before the update through a `FROM (SELECT id, proof ... WHERE code_hash = $1 FOR UPDATE)` self-join on `id`, so it comes back exactly once). A concurrent second exchange finds `code_hash` already null. The row, with its `state_hash` and `claimed_at`, stays until the sweep, so a replay of the provider return after a successful exchange is still recognised by `take`. No row: `handoff_failed` (`code_unknown`), 400. Then `base64url(sha256(codeVerifier))` is compared with `code_challenge` by `timingSafeEqual`; a mismatch records `pkce_mismatch` and answers 400 (the code is already gone). For `link`, the exchange itself compares the row's `auth_user_fk` and `session_id` with the Bearer claims before anything else runs; a missing Bearer or a mismatch records `link_caller_mismatch` and answers 403 (`dispatchIntent`'s own check would only answer `refused: expired`, which hides the cause). Then it unseals the transaction and the proof and calls change 2's `dispatchIntent({ event, authServer: supabaseAuthServer(event), verifiedToken: locals.verifiedToken }, tx, proof)`, so GoTrue's per-IP limits on `/token` see the app user's own address; the `signedIn` outcome's session (already past change 2's contested refresh) is answered in the body, never written as a cookie. For `signin`, a refusal ("sign in and link from settings", or `deleted` for an account with change 1's deletion marker, whose session change 2 already ended) is answered with change 2's message key. For `link`, `dispatchIntent` runs change 2's grant peek, `decideLink`, `bindLinkGrant` and `linkIdentity` (through `supabaseAuthServerAs(event, verifiedToken)`), which change 1's identity trigger lets through by spending the grant bound to that verified subject, and signs out the link's throwaway session.

Spending before the PKCE check is deliberate: a wrong verifier means the code reached someone else, and the legitimate app then starts over (resolved assumption 5).

What PKCE gives: it binds a code to the app that registered the challenge, so an app that merely catches another app's redirect cannot redeem it. It does not authenticate the app; what that leaves open is the client-impersonation entry in Risks.

Rejected: a separate `/api/app/v1/oauth/<provider>/callback` registered as a second return URL (one registered return URL per provider, and issuer, nonce, signature and linking checks exist once); storing the GoTrue session at the callback (a refresh token at rest; the ID token is the provider's and expires on its own); a URL-parameter state on the return for the app to check (PKCE already binds the code to the app that started the flow); the private-use scheme for grnyte's own iOS app (another app could catch its code, and iOS 17.4 gives an https return for free); an https return on Android now (needs a Chrome Auth Tab module Expo does not ship, deferred to the native project); `preferEphemeralSession` in `openAuthSessionAsync` on iOS (nothing to isolate, since this path sets no cookies, and it would hide Safari's Google session from the account picker).

### 5. Native Apple ID tokens: verified here, then change 2's rules

A native Apple ID token comes from the device, not from Apple's token endpoint over TLS, so change 2's trust in the code grant does not cover it, and for re-auth it never reaches GoTrue either. New `src/lib/auth/app/appleToken.server.ts`:

```ts
export async function verifyAppleIdToken(token: string, audience: string, nonceDigest: string):
  Promise<{ ok: true; claims: AppleClaims } | { ok: false; reason: 'invalid' | 'unavailable' }>
export async function exchangeAppleCode(code: string, clientId: string): Promise<{ refreshToken: string; sub: string } | null>
```

`verifyAppleIdToken` runs jose `jwtVerify` against `createRemoteJWKSet(new URL('https://appleid.apple.com/auth/keys'))` (one set per process, jose's default cooldown and cache) with `algorithms: ['RS256']`, `issuer: 'https://appleid.apple.com'`, `audience` pinned to the one value given, and `requiredClaims: ['sub', 'iat', 'exp', 'nonce']` (jose checks `exp`), then requires `claims.nonce === nonceDigest` (a plain comparison: both are public digests, and `timingSafeEqual` would throw on a nonce of another length). A JWKS fetch failure is `unavailable`, answered 503: classification is by place, not by error, so this change lifts `resolveKey`'s wrapper out of `verify.server.ts` as an exported `taggingJwks(jwks)` (it rethrows only what the key getter throws, except the no-match and multiple-match codes, as the exported `JwksUnavailable`) and passes Apple's `createRemoteJWKSet` through it; an expired token or bad signature thrown by `jwtVerify` stays `invalid`; everything else is `invalid`. It runs before any claim is read on every native Apple path: `oauth/apple/native`, `identities/link/apple` and `reauth/apple/confirm`. An `invalid` token records `handoff_failed` (`apple_token_invalid`) and answers one fixed `failed` refusal, the same whether or not any account has the address, so no unverified claim ever reaches `decideSignIn` or `decideLink`.

`exchangeAppleCode` posts `grant_type=authorization_code`, `code`, `client_id` and `client_secret = await appleClientSecret(clientId)` to `https://appleid.apple.com/auth/token`, with no `redirect_uri` (a native authorization code was issued without one), and returns Apple's refresh token and the `sub` of the ID token in Apple's answer (read from Apple's own TLS response, as change 2 trusts its code grant), or null.

**Sign-in on iOS.** The app draws a 32-byte raw nonce with `react-native-quick-crypto`, passes `sha256hex(raw)` to `AppleAuthentication.signInAsync({ nonce, requestedScopes: [EMAIL] })`, and posts `{ idToken, rawNonce }` to `oauth/apple/native`. The endpoint refuses when Apple is missing from `configuredProviders(event)`, runs `verifyAppleIdToken(idToken, APP_BUNDLE_ID, providerNonce(rawNonce))`, builds a `VerifiedProof` from the verified claims and calls `dispatchIntent({ event, authServer: supabaseAuthServer(event) }, signinTx, proof)` exactly as the exchange does (resolved assumption 2). GoTrue checks the nonce again. `APP_BUNDLE_ID = 'rocks.grnyte'` lives in new `src/lib/auth/app/constants.ts` with `APP_SCHEME_RETURN = 'rocks.grnyte:/auth'`, `APP_RETURN_PATH`, the `APP_RETURNS` allowlist (decision 4) and `APP_LINK_PREFIXES` (decision 8).

**Link on iOS** (`identities/link/apple`): the same verification, then `dispatchIntent` with a `link` transaction for the Bearer caller and `verifiedToken: locals.verifiedToken`, after the caller has an `identity.link` grant.

### 6. Native "Confirm with Apple"

`POST reauth/apple/start { action, target }`: Apple must be in `configuredProviders(event)`; `action` and `target` must pass change 2's `confirm`-intent validation (a valid `ReauthAction`, a target of that action's shape, a bare provider for `identity.*`), the same function, never a copy; the caller must have Apple among `signInMethods(sub).providers`. Any refusal answers 400 and stores nothing. Then it draws a 32-byte nonce, applies the start cap above (its row stores `client_hash` too), inserts a row with `purpose = 'reauth'`, only `nonce_digest = providerNonce(nonce)`, the caller's `auth_user_fk`, `session_id`, `action`, `target`, expiring in 5 minutes, and returns `{ flowId, nonce: nonce_digest }`. Nothing secret is stored: the digest is all Apple sees and all the check needs, and the raw value is discarded.

`POST reauth/apple/confirm { flowId, idToken, authorizationCode? }`, in new `src/lib/auth/app/appleReauth.server.ts`:

1. One statement spends the row: `DELETE ... WHERE id = $1 AND purpose = 'reauth' AND auth_user_fk = $sub AND session_id = $sid AND expires_at > now() RETURNING *`. No row: `handoff_failed` (`apple_reauth_mismatch`), 400.
2. `verifyAppleIdToken(idToken, APP_BUNDLE_ID, row.nonce_digest)` (decision 5).
3. Change 2's `acceptAppleConfirmation(caller, row.action, row.target, claims)`: the session and `sub` checks (`oauth_sub_mismatch`), then the `apple` grant. It runs before anything touches Apple, so a token for another Apple ID never reaches revocation.
4. Only when that answered `granted`, and for `account.delete` or `identity.unlink` with target `apple` (resolved assumption 8): `exchangeAppleCode(authorizationCode, APP_BUNDLE_ID)`; its returned `sub` must equal the verified token's `sub`, else nothing is revoked or recorded as revoked, `handoff_failed` (`apple_code_mismatch`) is recorded, and change 2 later records `apple_revoke_skipped`. On a match, `revokeAppleToken(refreshToken, APP_BUNDLE_ID)`; `true` records `apple_revoked` (detail `{ provider: 'apple', action, target }`, which change 2's deletion mail line and its `apple_revoke_skipped` check read), anything else `apple_revoke_failed`. The grant stands either way (change 2's rule); it can only be spent by a later request, after this one has finished revoking.

Age: no separate `iat` rule. The nonce is created at the start and the row expires 5 minutes later, so a token carrying it was necessarily issued within those 5 minutes; an `iat` check could never fire. That bound replaces change 2's 10-minute transaction for the native path.

Any refusal answers 400 with change 2's Apple-confirm failure key. The action and target come from the row, never from the confirm request, so a token obtained for one target cannot confirm another.

Sealing uses change 2's `seal` with info `grnyte app handoff v1`, so the key is derived from `SUPABASE_SECRET_KEY` under its own label like the transaction cookie's and no new secret exists; rotating that key orphans open handoff rows, which live 10 minutes.

### 12. Web sign-ins end on `/auth/continue`

A server redirect at the end of a chain that started on another site (Google's or Apple's consent, then `/auth/callback/<provider>`, then a 303 to `next`) can be handed to the installed app when `next` is a claimed content path, opening the app mid-flow while the session stays in the browser. An in-page navigation on grnyte's own origin is not handed to an app by iOS or Android, so every web sign-in or sign-up that arrives by redirect and ends on a `next` destination ends on new `src/routes/(landing)/auth/continue/+page.svelte` first, under the excluded `/auth`. A sign-in that already runs on grnyte's own page moves straight to `next` (user decision, 2026-11-16).

- One helper decides it. `$lib/auth/index.ts`: today's body of `signedInRedirectTarget` (`appPath(next) ?? APP_HOME_PATH`, same-origin through `sameOriginPath` and outside `/auth`) becomes exported `nextDestination(next)`, and `signedInRedirectTarget(next)` answers `` `/auth/continue?next=${encodeURIComponent(path)}` `` when `appPath(next)` gives a path, else `APP_HOME_PATH` directly (unclaimed, no hop). The redirects that arrive from elsewhere end through it: the OAuth provider return and a signed-in start (`oauth/flow.server.ts`), the hook's signed-in bounce off `/auth` (`leaveAuthPages`), and `auth/confirm/+server.ts`'s two success redirects (the contested and error branches are unchanged). Password sign-in (`signin.remote.ts`), code confirmation (`MailedCodeStep.svelte`) and the profile step (`profile.remote.ts`) start their navigation on grnyte's own page, so they answer `nextDestination(next)` and skip the hop: passing through it painted the page's copy for about half a second on every in-page sign-in (user decision, 2026-11-16).
- The page reads `next` from `page.url`, validates it again with `nextDestination` (a hand-typed `/auth/continue?next=//evil.com` lands on `/explore`), calls `location.replace(target)` on a document-load arrival (`afterNavigate`'s `enter`) or `redirectTo(target)` on a client arrival, and renders a plain `<a href={target}>` with `auth_continue*` copy for a reader without JavaScript. No load function, no session read, `replace` so Back does not return to it.
- The hook: `/auth/continue` joins `AUTH_PASSTHROUGH_PATHS`, so `leaveAuthPages` does not bounce a signed-in reader off it (which would loop through the helper) and `profileGate` lets it run; a profile-less account then reaches the content page in-page and the gate's own redirect sends it to the profile step with that `next`, which ends here again.
- Deferred fallback, not built: an Apple `components` exclusion on a marker query (`{ '/': '*', '?': { web: '1' }, exclude: true }` first in the list, and the page appending `web=1`), only if the real-device test (task 12.14) shows iOS still opening the app.

## Risks / Trade-offs

- [Client impersonation through the private-use scheme, on BOTH platforms: a malicious app starts its own grnyte sign-in naming the `android` channel with its own PKCE challenge, the person consents at the real provider, and the app catches `rocks.grnyte:/auth?code=` and keeps the session (RFC 8252 section 8.6). On iOS this works too, because `ASWebAuthenticationSession` accepts any callback scheme, `oauth/start` is unauthenticated and the server cannot tell which app named which channel; PKCE binds a code to whoever registered its challenge, which here is the impersonating app] → Accepted by the user on both platforms (proposal, return-channel ruling 1), as RFC 8252 does; no User-Agent check, which would prove nothing. This entry is the one statement of the risk; the spec and proposal point here. iOS cannot be said to be safe from it: the https return protects only grnyte's genuine app's own flow from interception. Follow-ups for the real native project: app attestation (Apple App Attest, Google Play Integrity, for example through Firebase App Check) so the server offers a return channel only to a verified copy of the app, and the Android Chrome Auth Tab on a verified https return where Chrome 137 or later supports it.
- [A web flow ends on a claimed path and iOS or Android opens the app mid-flow] → `APP_LINK_PREFIXES` holds content paths only, never settings, region account screens or `/auth`; `/explore`, `/profile` and `/invite` stay unclaimed, so a plain web sign-in and an invitation sign-in end in Safari; a sign-in whose `next` is a content path ends on the unclaimed `/auth/continue` and reaches it in-page (decision 12). Device tests drive a web link, a plain web Google sign-in and a Google sign-in started on a content page with the app installed (tasks 12.13, 12.14); the `?web=1` exclusion is the fallback if iOS still opens the app.
- [The iOS return renders as a page and leaks the code] → The page never reads the query, `csr = false`, `no-store`, `no-referrer`; task 7.6 asserts no script and no markup carries the code.
- [After the sweep, a replayed app state falls through to the web carrier, which spends any web sign-in in progress in that browser's cookie] → Accepted: it needs a replay over an hour late in the same browser, and the web sign-in reads as expired and can be started again.
- [The iOS https return fails at start with `ASWebAuthenticationSession` error `Code=1` "requires webcredentials", seen on the Simulator and for some users whose device has not fetched the association file] → The test app shows the start error; a real device is the expected verifier (task 12.6). If it recurs on devices, the fallback is the scheme channel, which carries the impersonation risk above.
- [Change 2's carrier list or `dispatchIntent` turns out cookie-bound, or `completeOAuth` swallows a `take` that throws] → Task 2.1a checks the seam with a stub carrier before anything here builds on it, and task 7.3 proves the real app carrier reaches the same outcome as the web carrier; a gap is fixed inside change 2's module, never copied here.
- [Change 1's seeded in-memory storage stops working in a supabase-js release] → `supabaseAuthServerAs` is the one user-scoped client, now also for `signOut({ scope: 'others' })`, `getUserIdentities` and `unlinkIdentity`; a GoTrue-backed test drives sign out other devices through it with a Bearer caller (task 6.6c), so an upgrade fails a test, not production.
- [Apple rotates or adds keys] → jose refetches the JWKS on an unknown `kid` after its cooldown; a fetch failure is a 503, not a refusal.
- [Chrome Custom Tabs keep a server redirect to a custom scheme in the browser] → Driven on the Android emulator (task 12.7); if it stalls, `appCarrier.land` answers a tiny page with a "Return to the app" link to the same `rocks.grnyte:/auth?code=` URL, inside the 60 s.
- [The shared callback reads or rotates a web session in the in-app browser] → The hook loads no session on `/auth/callback/*` before a carrier is known (change 2) and the app carrier sets nothing; task 7.3 pins it with near-expiry web cookies attached.
- [Sign in with Apple does not run on the iOS Simulator] → The simulator signed into an Apple ID is tried first; only if it cannot show the sheet does a real iPhone verify native Apple and "Confirm with Apple", recorded as such. GoTrue's acceptance of the bundle ID as an audience is proven only with a real token (task 12.8).
- [A database reader or zero-cache's replica sees a handoff row] → Hashes and sealed values only (resolved assumption 4); every row dies within 70 minutes.
- [Apple's CDN caches the association file] → `?mode=developer` on the test app's associated domain fetches it directly on development devices.
- [An installed app pins today's endpoint shapes forever] → Own `v1` shapes, a contract snapshot, the widen-only rule in the spec and AGENTS.md; a breaking change ships as `v2` beside `v1`. The three carved-out answers (security refusal, update required, `v1` retired) keep hardening and sunsetting possible.
- [Android "Confirm with Apple" does not exist, so an Apple-linked deletion or Apple unlink from Android never revokes] → Accepted by the user: native "Confirm with Apple" is iOS only, because Apple's revocation requirement is an App Store rule binding the iOS app; change 2 records `apple_revoke_skipped`. A browser "Confirm with Apple" on Android through the handoff (a `confirm` purpose on `oauth/start`) is a follow-up.

## Migration Plan

1. Changes 1 and 2 are applied first in the same release branch.
2. Local, on the branch's second stack: GoTrue Apple client ID list, the ngrok Google callback, `ANDROID_CERT_SHA256` from the debug keystore, `IOS_APP_ASSOCIATION_ENABLED=true` (the Apple file, and with it `webcredentials`, answers 404 without it), migrate a throwaway DB, run the server tests. There is no hosted dev project.
3. Prod, by hand before the deploy: Apple client ID list (`APPLE_TEAM_ID` is already there from change 2); `IOS_APP_ASSOCIATION_ENABLED`, `ANDROID_CERT_SHA256` and `APP_MIN_VERSION` stay unset until a native app ships; `check:prod` passes, with both link files reported as not configured yet.
4. Deploy with changes 1 and 2. Nothing calls `/api/app/` until a native app ships.
5. Rollback: revert the deploy. The table is inert without callers; the link files disappear with their routes, which only matters once a native app is installed; the `/auth/continue` hop goes with the helper and its page together.
