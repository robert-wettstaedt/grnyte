### Round 4 (reader) paraphrase

**What this proposes.** A new `POST /api/webhooks/apple/sign-in` endpoint takes Apple's Sign in with Apple server-to-server notifications, verified by a shared `verifyAppleJwt` on Apple's existing key set (issuer, grnyte's two audiences, `iat` within the last day). `email-disabled` / `email-enabled` for a relay address write one hashed row per account to a new server-only `apple_mail_forwarding` table; while the current address is marked as not forwarding, grnyte's own mail to it returns `'suppressed'`, the email screen shows a banner (Apple linked: turn forwarding on, then change the address; not linked: write to support), and re-authentication says no code can arrive. `consent-revoked` / `account-deleted` sign out sessions created before the event and remove the Apple identity when another way in remains (kept otherwise), guarded by a new last-way-in floor and a marker rule 2b in `guard_auth_identity`; `account-deleted` also marks the relay as dead and never deletes the grnyte account. Stale, replayed, or within 10 minutes of grnyte's own `apple_revoke_started`, these change nothing; every notification Apple signed for grnyte is logged with type and outcome, other refused requests are only `console.warn`ed.

**How the existing system works, per this plan.** `unlinkProvider` checks `accountMethods().canUnlink` in an unlocked read, then has GoTrue unlink behind an `identity.unlink` grant that `guard_auth_identity` spends, and `keepAddress` puts back an address GoTrue moved. On a confirmed account the trigger allows an identity delete only through transaction-local markers, an unconfirmed account, or a live session-bound grant; nothing in the database stops the last way in from being removed. Apple ID tokens are verified with `jwtVerify` through `taggingJwks` on one per-process key set. grnyte's own mail goes through `sendEmail` / `sendEmailOutcome` to Resend, GoTrue's over SMTP. "Confirm with Apple" revokes at Apple, then records `apple_revoked`, which `hasRecentAppleRevocation` checks over 10 minutes; `deleteAccount` signs out by deleting `auth.sessions`.

Ruling: matches the intent.

## Paraphrases

### Round 1 (reader)

**What this proposes.** A new `POST /api/webhooks/apple/sign-in` endpoint receives Apple's Sign in with Apple server-to-server notifications. It verifies them with Apple's existing key set through a shared `verifyAppleJwt`. On `email-disabled` / `email-enabled`, a new server-only table records, per account, whether the relay address still forwards. While the current address does not forward, `sendEmail` suppresses grnyte's own mail to it, settings marks the email row, the email screen shows a banner, and the re-authentication step says no code can arrive. On `consent-revoked` / `account-deleted`, every session is ended and the Apple identity is removed when another way in remains (kept otherwise); the grnyte account is never deleted. Notifications that are stale or replayed (judged by `event_time`), or that arrive within 10 minutes of grnyte's own Apple revocation, are ignored, and each notification is logged with its type and outcome.

**How the existing system works, per this plan.** Removing a provider keeps the account's address (`keepAddress` puts it back if GoTrue moved it). On a confirmed account, the `guard_auth_identity` trigger allows an identity delete only through a transaction-local marker or a live, session-bound re-auth grant. Native Apple ID tokens are verified with `jwtVerify` against one per-process remote key set wrapped in `taggingJwks`, so a key outage (`JwksUnavailable`) is told apart from an invalid token. grnyte's own mail goes through `sendEmail` / `sendEmailOutcome` to Resend, while GoTrue sends its own over SMTP. Auth events are logged and failure kinds raise spike alerts; "Confirm with Apple" revokes at Apple and records `apple_revoked`, which later flows check over 10 minutes; `deleteAccount` signs out by deleting `auth.sessions`.

Ruling: both paraphrases match the intent.
