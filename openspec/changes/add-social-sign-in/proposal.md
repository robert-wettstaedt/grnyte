# Proposal

## Why

People who climb already have an Apple or Google account, and asking them for one more password costs sign-ups and, on iOS, would block the coming native app (App Store rule 4.8 requires Apple once Google is offered). This is change 2 of 3 from the social-login grilling, released together with `harden-auth-codes` and `add-native-auth-handoff` (no feature flag): it adds "Continue with Apple" and "Continue with Google" on top of the codes, re-authentication, profile step and screen slot that change 1 lays down.

## What Changes

- **Own OAuth client on grnyte's domain.** grnyte's server runs the authorization code flow with Apple and Google itself (PKCE, `state`, nonce) using `openid-client` 6.8.8, and hands the provider's ID token to Supabase's `signInWithIdToken`. The consent screen and the iOS dialog name grnyte, not `<ref>.supabase.co`, and the Apple client secret is minted per request from the `.p8` key, so it never needs rotating. GoTrue's own redirect flow stays the documented fallback and is not built.
- **One transaction per sign-in.** A sealed, HttpOnly, `SameSite=Lax`, 10-minute transaction cookie holds the PKCE verifier, the raw nonce, `state`, the intent and the destination; it is deleted on first use. Each provider has its own callback path with the provider pinned, `iss` is checked when returned, the provider receives `sha256hex(nonce)` and Supabase the raw value. The destination is validated as a same-origin path at the final redirect, never trusted from a URL parameter. Google gets `prompt=select_account` and `hl`, Apple `locale`.
- **Apple's `form_post` becomes a same-origin GET.** Apple posts its answer cross-site, where no `Lax` cookie travels; the callback answers that POST with a 303 to the same callback as a GET, so every grnyte cookie stays `SameSite=Lax` and linking and "Confirm with Apple" see the session. That POST is one of the exemptions in change 1's cross-site refusal, beside the app API, and reads no session.
- **One callback per provider, two carriers.** The callback finds the sign-in by its `state` through a list of transaction carriers: this change's web carrier (the cookie) and `add-native-auth-handoff`'s app carrier (a server row). Issuer, audience, nonce and linking checks exist once, and Apple and Google allow-list one return URL each. GoTrue verifies the ID token's signature for sign-in and link; for "Confirm with Apple" the token comes straight from Apple's token endpoint over TLS with client authentication, which OpenID Connect allows in place of a signature check.
- **Account matching rules.** A provider sign-in onto a confirmed account that has no identity of that provider is refused unless the provider owns the address's domain; the person is told to sign in and link from settings. The database trigger from change 1 allows exactly that domain case on its own, so no grant is written for it. A sign-in onto an unconfirmed account follows GoTrue's default and clears the contested-sign-up flag. A new person passes the profile step from change 1.
- **Sign-in methods in settings.** A new settings screen lists the account's password and its Apple and Google identities, links a provider after re-authentication, unlinks one after re-authentication unless it would leave no way in, offers "Set a password" to an account without one, and takes over change 1's "Sign out other devices" row and signed-in devices list. Linking refuses an identity already on another account and a provider address that belongs to another account. No prompt to add a second method anywhere.
- **"Confirm with Apple".** Every re-authentication screen of an Apple-linked account offers an Apple sign-in in place of the mailed code, before any code is mailed. It proves control of the Apple ID signed in on this browser, not a fresh login, and is bound to the account's own Apple identity and session, completed within the sign-in's 10 minutes, with a nonce bound to that action and target. Deleting the account and unlinking Apple use it to revoke grnyte's Apple authorization; nothing from Apple is stored.
- **A choice in change 1's first-step slot.** `/auth/signin` and `/auth/signup` open on "Continue with Apple", "Continue with Google" and "Continue with email"; the email form follows on the same page. The provider buttons are self-drawn to both brand guides ([Apple](https://developer.apple.com/design/human-interface-guidelines/sign-in-with-apple), [Google](https://developers.google.com/identity/branding-guidelines)), no third-party script before a click. The device remembers the last method used (`apple`, `google`, `email`, never the address) and badges that button on its corner. Logos are hidden from assistive technology, each button has one text label, and both wrap at 200 % zoom. The failed sign-in message gains the fixed "Signed up with Apple or Google?" hint.
- **Callback error states.** One error screen by reason: a cancelled sign-in returns quietly to where it started; an expired or failed one offers "Try again"; offline says so; a refused match or link conflict says what to do instead.
- **Invitation address mismatch copy.** `This invite is for <address>. Continue with that email, or ask <inviter> to invite the address you use.`, with "an admin of <region>" when the inviter's account is gone. Accepting stays strict.
- **Configuration and outside setup.** Apple and Google enabled on GoTrue for ID tokens (Services ID and the web client ID first in each list), manual linking and the identity-linked/unlinked notifications on, all asserted by `npm run check:prod`. Apple Developer Program as Individual, Google brand verification started once the consent screen exists, the From domain and Resend's Return-Path subdomain registered with Apple's private relay, ngrok with a free static domain for local Apple testing, a device test of the round trip from the installed PWA on iPhone and Android Chrome, and the privacy policy naming Apple and Google and what their sign-in stores.

No existing URL, remote export or `manifest.id` changes. The new callback URLs are registered at Apple and Google and must never move. Already-loaded tabs across the deploy keep working: they show change 1's screens without buttons until their next load, and none of them calls anything this change removes.

## Non-goals

- The native app side, all in `add-native-auth-handoff`: Bearer-token app endpoints, the app start endpoint and app carrier, the `rocks.grnyte:/auth` handoff, `apple-app-site-association` and `assetlinks.json`, native Apple sign-in, and the Expo test app. This change only shapes its callback and carrier list so that change plugs in an app carrier without editing them.
- GoTrue's redirect flow (the fallback if the own client fails): documented, not built.
- Reading or showing a provider's name or avatar. Bot friction beyond the provider and GoTrue's IP limits. Apple server-to-server notifications and Google RISC.
- Providers other than Apple and Google. Passkeys and MFA. Any "add a second sign-in method" prompt.
- A feature flag or a staged launch.
- Everything change 1 already owns: codes, the re-authentication mechanism and its database guard, the profile step and gate, session revocation, the before-user-created hook, the sign-in screens themselves.

## Capabilities

### New Capabilities

- `auth/social-sign-in`: signing in and creating an account with Apple or Google on the web, the transaction that carries one sign-in, how a provider identity is matched to an account, the callback's outcomes and error states, and the provider configuration a deployed environment must have.
- `auth/sign-in-methods`: the settings screen that lists an account's ways in, linking and unlinking a provider, the conflicts that refuse a link, and setting a first password.
- `regions/invitations`: what the invitation screen says when the signed-in account's address is not the invited one.

### Modified Capabilities

- `auth/reauthentication` (introduced by `harden-auth-codes`): an Apple sign-in confirms in place of the code for Apple-linked accounts, under binding rules of its own, and a refused action on such an account offers Apple again instead of mailing a code at once.
- `auth/sign-in-screens` (introduced by `harden-auth-codes`): the first step is a choice of Apple, Google and email, with fixed wording and order, the last-used badge, accessibility rules, and the hint on a failed sign-in.
- `auth/security-notices` (introduced by `harden-auth-codes`): linking and unlinking a provider mail a notice.
- `auth/account-deletion`: deleting an Apple-linked account revokes grnyte's Apple authorization.

## Resolved assumptions

Each was a choice no decision entry covered, or a reading of one the code forced; the user ruled on all of them (2026-11-09). Specs, design and tasks follow these rulings.

1. **Apple's `form_post` is answered with a 303 to a same-origin GET, and every auth cookie stays `SameSite=Lax`** (replacing the earlier `SameSite=None` on Apple's path). (`auth/social-sign-in`)
2. **Replaced:** change 1's `auth.identities` trigger itself allows the provider-owned domain insert when the identity's address equals the account's, so this change writes no grant for it and no `'provider_domain'` grant method exists. (`auth/social-sign-in`)
3. **`ReauthStep` peeks for a live grant before mailing a code**; the peek moved into `harden-auth-codes`, so coming back from Apple mails nothing. (`auth/reauthentication`)
4. **Apple-linked deletion and Apple unlink lead with Apple and still accept the code**, recording `apple_revoke_skipped`, as written. (`auth/account-deletion`, `auth/sign-in-methods`)
5. **Revocation runs at the Apple confirmation, before the grant is written**, as written. (`auth/account-deletion`)
6. **The deletion mail's revocation line** reads an `apple_revoked` event from the last 10 minutes, as written. (`auth/account-deletion`)
7. **The transaction cookie is sealed** (JWE, `dir` + `A256GCM`, `jose`) under a key from change 1's `labelledKey` (derived from `SUPABASE_SECRET_KEY`, no secret of its own; changed in `harden-auth-codes` review round 2); `add-native-auth-handoff` seals its rows with the same helper. (`auth/social-sign-in`)
8. **The last-used method is a first-party cookie the server reads**, 400 days, as written. (`auth/sign-in-screens`)
9. **Scopes are minimal** (Google `openid email`, Apple `email`), as written. (`auth/social-sign-in`)
10. **A provider's button renders only where it is configured**, and `check:prod` asserts both on the deployed page, as written. (`auth/sign-in-screens`)
11. **The refusal to auto-link onto a confirmed account says an account exists for that address**, as written. (`auth/social-sign-in`)
12. **The settings "Password" row becomes "Sign-in methods"**, and the password screen titles itself "Set a password" when there is none, as written. (`auth/sign-in-methods`)
13. **Unlink needs an identity count of at least 2 and a password or another provider left**, as written. A first password writes GoTrue's `email` identity (`harden-auth-codes` task 8.4d), so a social-only account that sets one can then remove its provider. (`auth/sign-in-methods`)
14. **The installed-PWA fallback (a "Return to the app" handover if the callback lands outside the PWA) is not designed here**; the device test decides and raises it, as written. (`auth/social-sign-in`)
15. **Kit's CSRF check trusts `https://appleid.apple.com`**, as written; change 1's cross-site guard exempts the same POST. (`auth/social-sign-in`)
16. **Confirm with Apple proves control of the Apple ID signed in on this browser, not a fresh login** (ruled after plan review round 1). Apple's documented ID token claims include no `auth_time` and its `iat` is the exchange moment, so no age rule applies: freshness is bounded only by the 10-minute transaction, and Apple may confirm without a prompt. An unlocked device holding both a grnyte and an Apple session can confirm; accepted as comparable to the mailed code with Mail on the same device. Which claims Apple sends is recorded in task 12.2. (`auth/reauthentication`)
17. **The extra event kinds** (`oauth_link_refused`, `oauth_sub_mismatch`, `apple_revoked`, `apple_revoke_failed`, `apple_revoke_skipped`), as written. (`auth/social-sign-in`)
18. **The start is a form POST** guarded by Kit's origin check and change 1's cross-site guard, as written. (`auth/social-sign-in`)
19. **Removing a provider at an address it owns re-links on the next "Continue with" sign-in** (ruled after plan review round 1, accepted as is). The inline Remove step says so; no record of unlinked providers is kept. (`auth/sign-in-methods`, `auth/social-sign-in`)
20. **Unlinking signs the account's other devices out; linking does not** (ruled after plan review round 1). The caller's own session stays signed in. (`auth/sign-in-methods`)
